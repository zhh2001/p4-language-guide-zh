# 05 · 类型系统

本章介绍 P4_16 如何表示数值、报头和元数据，重点区分类型、初始化和报头有效性。语言规则以 [P4_16 规范 v1.2.5](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html) 为依据，编译验证使用本机 p4c 1.2.5.10，报文验证使用 BMv2 `simple_switch` 1.15.0-2bdd0b7b。

P4 没有 C 风格的指针和浮点类型。它提供精确到位的整数、带有效位的报头，以及用于组织数据的结构体、元组等类型。语言允许某种类型，并不保证每个目标都能实现它；位宽、对齐和可用操作还可能受后端限制。

本章代码以片段为主。类型声明放在声明区域，局部变量与操作放在允许的执行位置；片段中引用的其他类型、报头或 extern 需要事先声明。编译检查的方法见 [4.16 节](./04-语法基础.md#416-编译检查与本章小结)。

## 5.1 基本类型一览

| 类型         | 含义                                        |
| ------------ | ------------------------------------------- |
| `void`       | 表示函数或方法没有返回值                    |
| `bool`       | 布尔值 `true`、`false`                      |
| `error`      | 错误标识，如 `error.PacketTooShort`         |
| `string`     | 编译期已知的字符串                          |
| `match_kind` | 匹配方式标识，如 `exact`、`lpm`             |
| `int`        | 编译期使用的任意精度整数                    |
| `bit<W>`     | W 位无符号整数，也称位串                    |
| `int<W>`     | W 位有符号整数，采用二进制补码              |
| `varbit<W>`  | 实际宽度在运行时确定、最大宽度为 W 位的位串 |

`int` 与 `int<W>` 是不同类型：前者没有固定的存储宽度，不能用来声明普通运行时变量。

## 5.2 `void`

`void` 用于声明不返回值的函数或方法，不能作为变量或报头字段的类型。

```p4
void clear_value(out bit<8> value) {
    value = 0;
}
```

这个函数通过 `out` 参数输出数据，调用表达式本身没有返回值。

## 5.3 `error`

`error` 是一个可扩展的错误标识类型，多个顶层声明为同一个类型增加成员：

```p4
error { BadIPv4Version }
error { InvalidIhl }
```

使用时写成 `error.BadIPv4Version`。成员不能在源码中指定整数编码，也不能重复声明已有成员。`core.p4` 已经定义 `NoError`、`PacketTooShort`、`StackOutOfBounds` 等成员，不应再次定义。

同类型错误值可以赋值，或用 `==`、`!=` 比较。Parser 中常见的用法是 `verify(条件, error.BadIPv4Version)`；失败后的状态转移见 [第 6 章](./06-Parser解析器.md)。

## 5.4 `match_kind`

`match_kind` 描述表键采用什么匹配方式。核心库已有以下声明：

```p4
match_kind { exact, ternary, lpm }
```

这里展示的是核心库内容，包含 `core.p4` 的程序不需要再写一遍。表键直接使用 `exact` 等名字，不加 `match_kind.` 前缀。

新增匹配方式属于架构描述的职责，还需要目标和控制平面提供对应实现。在普通程序中自行增加一个名字，并不会让交换机获得新的匹配能力。

## 5.5 `bool` 与 `string`

`bool` 只有 `true`、`false` 两个值，不与整数隐式互换。`if (x)` 要求 `x` 为 `bool`；整数条件应写成 `if (x != 0)` 等形式。

`string` 用于编译期已知值，可以声明 `const string` 常量，不能声明可修改的字符串变量。它常用于注解和静态断言，不能作为报文负载的存储类型。示例与转换规则见 [4.5.4 节](./04-语法基础.md#454-字符串)和 [4.15 节](./04-语法基础.md#415-显式与隐式类型转换)。

## 5.6 整数类型

### 5.6.1 无符号 `bit<W>`

对于正位宽 W，`bit<W>` 的取值范围为 `0` 到 `2^W - 1`。W 必须是局部编译期已知的非负整数，不能由当前报文决定。规范还允许 `bit<0>`，其唯一值为 0；目标可以限制实际支持的位宽。

```p4
const int BASE_WIDTH = 10;
const bit<(BASE_WIDTH + 2)> LIMIT = 15; // 类型为 bit<12>
```

复合位宽表达式需要括号。`bit` 是 `bit<1>` 的简写，不是任意宽度的位串。

位编号从最低有效位 0 开始，最高有效位为 W−1。固定位宽算术不会自动增加结果位宽，例如 `8w255 + 8w1` 得到 `8w0`。

### 5.6.2 有符号 `int<W>`

`int<W>` 使用二进制补码，W 至少为 1，取值范围为 `-2^(W-1)` 到 `2^(W-1)-1`。例如，`int<8>` 的范围是 −128 到 127，`int<1>` 只能表示 −1 和 0。

固定位宽有符号运算也按位宽保留结果。例如，`8s127 + 8s1` 得到 −128。P4 不会像某些 C 表达式那样先提升到较宽的 `int` 再计算。

混合位宽或符号性的算术通常需要显式转换。运行时移位量须为无符号整数；编译期已知的非负整数也可用作移位量，不能笼统地说“所有有符号移位量都不合法”。详见 [4.15 节](./04-语法基础.md#415-显式与隐式类型转换)。

### 5.6.3 动态宽度 `varbit<W>`

`varbit<W>` 同时具有编译期确定的最大宽度 W 和运行时确定的实际宽度。IPv4 选项是一个典型用途：

```p4
header IPv4_options_h {
    varbit<320> options;
}
```

这里的 320 是最大位数。Parser 可以用双参数 `extract` 提取这个报头，第二个参数给出其中 `varbit` 字段的实际位数；该提取形式只支持一个可变长字段。长度不能超过声明上限，目标还可能要求按字节提取。

`varbit` 支持的操作包括：

- 相同类型之间的赋值，同时复制实际宽度和数据；
- 相同类型之间的 `==`、`!=` 比较，相等要求实际宽度及有效数据位都相同；
- 通过包含它的报头进行 `extract` 和 `emit`。

例如，假设 `hdr.original` 与 `hdr.copy` 均为 `IPv4_options_h`，且前者已成功提取：

```p4
hdr.copy.setValid();
hdr.copy.options = hdr.original.options;
```

即使实际数据都只有 16 位，`varbit<320>` 与 `varbit<160>` 也不是相同类型，不能直接互相赋值。`varbit` 不支持普通整数算术、位切片或到 `bit<W>` 的直接转换。未初始化的 `varbit` 实际宽度也没有保证。

### 5.6.4 任意精度 `int`

`int` 用于编译期整数计算，可以引用此前声明的常量，并不限于直接拼接字面量：

```p4
const int BASE = 5;
const int DOUBLE_BASE = 2 * BASE;
const int LARGE = 1 << 80;
```

不能写一个普通的 `int counter;` 来计数运行时事件，应选用目标支持的固定位宽类型。允许接收 `int` 的参数必须无方向，实参须在编译期已知；动作参数不能使用 `int`。

## 5.7 `enum` 枚举

普通枚举定义一组有名字的值，不规定其整数编码：

```p4
enum ParseStatus { NotParsed, Parsed, Unsupported }
```

它可以用于变量、结构体成员、赋值、相等／不等比较以及 `switch` 等分支，不能直接作为报头字段，也不能把成员顺序当作整数值。

可序列化枚举显式指定底层固定位宽整数类型和每个成员的编码：

```p4
enum bit<16> EtherType {
    IPV4 = 0x0800,
    ARP  = 0x0806,
    IPV6 = 0x86DD
}
```

底层类型可以是 `bit<W>` 或 `int<W>`，成员值必须在相应范围内。枚举值可隐式转为底层类型，反方向需要显式转换。可序列化枚举还可能保存未命名的编码，见 5.14 节。

## 5.8 `header`：带有效位的报头

`header` 将字段布局与有效性结合起来。有效位用于决定这个报头当前是否存在，不是报文线上额外携带的一位，也不代表校验和或协议内容一定正确。

### 5.8.1 声明与字段布局

```p4
header Ethernet_h {
    bit<48> dstAddr;
    bit<48> srcAddr;
    bit<16> etherType;
}
```

字段按声明顺序排列，语言不在它们之间自动插入填充位。上例的序列化长度为 112 位，即 14 字节，不包含有效位。目标可能另行限制报头必须按字节对齐。

直接字段可以使用 `bit<W>`、`int<W>`、`varbit<W>`、`bool` 和可序列化枚举。`bool` 在线上占一位，0 表示 `false`，1 表示 `true`。报头不能嵌套另一个报头、报头联合体或报头栈。

报头可以包含用于组织字段的 `struct`，但这些结构体的最终叶子字段只能是固定位宽整数、`bool` 或可序列化枚举。例如：

```p4
struct IPv6Address {
    bit<32> word0;
    bit<32> word1;
    bit<32> word2;
    bit<32> word3;
}
header IPv6_h {
    bit<4> version;
    bit<8> trafficClass;
    bit<20> flowLabel;
    bit<16> payloadLen;
    bit<8> nextHdr;
    bit<8> hopLimit;
    IPv6Address src;
    IPv6Address dst;
}
```

结构体内部同样按声明顺序展开。本例长度为 320 位，即 40 字节。完整嵌套规则见规范[第 7.2.8 节](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-type-nesting)。

### 5.8.2 空报头

```p4
header Empty_h { }
```

空报头没有数据字段，仍然具有有效位，可以区分有效与无效状态。

### 5.8.3 有效位与字段初始化

没有显式初始化的局部报头变量最初无效。成功的 `extract` 会填入字段并使报头有效；手工构造报头时，可以先使其有效，再初始化所有需要读取或输出的字段：

```p4
Ethernet_h eth;
eth.setValid();
eth.dstAddr = 48w0x02_00_00_00_00_02;
eth.srcAddr = 48w0x02_00_00_00_00_01;
eth.etherType = 0x0800;
```

**`setValid()` 不初始化字段。** 向无效报头写字段，也不会自动使报头有效；先写字段、后调用 `setValid()`，不能保证此前写入的值随后可用。读取无效报头的字段，或读取有效报头中尚未初始化的字段，得到的值都没有规定，不能依赖某次 BMv2 运行恰好读到了什么。相关规则见规范[第 8.25 节](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-uninitialized-values-and-writing-invalid-headers)。

`packet_out.emit` 跳过无效报头。使报头有效也不会自动输出它，Deparser 仍需执行对应的 `emit`。

### 5.8.4 整体初始化与赋值

```p4
header Pair_h {
    bit<16> first;
    bit<16> second;
}
```

在执行位置可以写：

```p4
Pair_h pair;
pair = { 10, 12 };                  // 按声明顺序填入字段，报头有效
pair = { second = 12, first = 10 }; // 按字段名填入，报头有效
pair = (Pair_h){#};                // 报头变为无效
```

同类型报头之间的赋值会复制字段及有效位。`{#}` 是无效报头表达式；编译器无法推断具体类型时，需要显式转换。本机编译器会拒绝上例中直接写成 `pair = {#};` 的形式，因此这里明确标注 `Pair_h`；也可以调用 `pair.setInvalid()`。

### 5.8.5 比较

两个报头必须类型相同才能使用 `==`、`!=`。相等规则是：

| 两个报头的状态 | `==` 的结果                 |
| -------------- | --------------------------- |
| 都无效         | `true`，不比较字段          |
| 只有一个有效   | `false`                     |
| 都有效         | 所有对应字段相等时为 `true` |

规范中的 `h == {#}` 等价于 `!h.isValid()`；实际代码直接查询有效位，可以避免无效报头表达式的类型推断问题。不能因为两个无效报头曾经保存过不同字段值，就认定它们不相等。

### 5.8.6 方法

| 方法             | 作用                           |
| ---------------- | ------------------------------ |
| `h.isValid()`    | 查询有效位                     |
| `h.setValid()`   | 使报头有效，不填充字段         |
| `h.setInvalid()` | 使报头无效，后续不应依赖字段值 |

`setValid()`、`setInvalid()` 要求可写的报头对象；不能对只读的 `in` 参数调用它们。

## 5.9 报头栈 `header stack`

报头栈是元素类型相同、容量在编译期确定的数组，元素可以是报头或报头联合体。它常用于连续的 MPLS 标签或 VLAN 标签，不是可以在运行时扩容的容器。

```p4
header Mpls_h {
    bit<20> label;
    bit<3> tc;
    bit<1> bos;
    bit<8> ttl;
}
struct MplsHeaders {
    Mpls_h[3] labels;
}
```

这里为最多 3 个标签预留位置。每个元素有自己的有效性，有效元素不必连续；容量为 3 不表示报文中一定有 3 个标签。

### 5.9.1 解析索引

报头栈在概念上维护 `nextIndex`，初始化为 0，用来支持 Parser 中的顺序提取。它不是普通的用户可写字段，也不是“当前有效报头数量”。

当 `packet.extract(hs.next)` 成功时，解析索引递增。对 `hs[i]` 的普通字段赋值、`setValid()`，或仅仅访问 `hs.next`，都不等于成功提取下一个元素。只读 `hs.last`、`hs.lastIndex` 也不会推进索引。

### 5.9.2 操作与边界

| 表达式             | 语义                                                                      |
| ------------------ | ------------------------------------------------------------------------- |
| `hs[i]`            | 访问下标 i 的元素；有些目标只支持编译期常量下标                           |
| `hs.size`          | 容量，类型为 `bit<32>`，是局部编译期已知值                                |
| `hs.next`          | Parser 专用，引用 `nextIndex` 对应元素，可作提取目的地                    |
| `hs.last`          | Parser 专用，只读地引用 `nextIndex - 1` 对应元素                          |
| `hs.lastIndex`     | Parser 专用，返回 `bit<32>` 类型的 `nextIndex - 1`；索引为 0 时结果未规定 |
| `hs.push_front(n)` | 元素向较大下标移动 n 个位置，前 n 个位置无效，尾部超出的元素丢弃          |
| `hs.pop_front(n)`  | 元素向较小下标移动 n 个位置，移出的前部元素丢弃，尾部空位无效             |
| `hs = other`       | 同类型、同容量的栈整体赋值，包括有效位和解析索引                          |
| `hs == other`      | 同类型、同容量的栈逐元素比较，解析索引不参与                              |

`push_front`、`pop_front` 的 n 须在编译期已知；本章使用正整数。两者还分别增加、减少 `nextIndex`，并将其限制在 `[0, hs.size]` 范围内。移动的是报头元素，不是报头内部的比特位。

本机 p4c 不允许在 Parser 内调用 `push_front`、`pop_front`，应把相应修改放在 Control 或动作中。`next`、`last`、`lastIndex` 则只允许在 Parser 内访问，不能拿到 Ingress 中继续使用。

编译期已知下标越界必须报错。目标若支持运行时下标，越界访问也不能当作安全的普通读写。`next`、`last` 有专门规则：越界会使 Parser 进入 `reject`，错误为 `error.StackOutOfBounds`；它们与 `hs[i]` 的越界行为不同。

### 5.9.3 初始化

下面沿用 5.8.4 节的 `Pair_h`，放在允许声明局部变量的位置：

```p4
Pair_h[3] pairs = { { 0, 1 }, { 2, 3 }, ... };
```

前两个元素有效，第三个使用默认值而无效。这种初始化并不表示 Parser 已经从报文中提取了两个元素，不能据此把解析索引理解为 2。

这段写法符合语言规范，但本机工具链存在实现问题：p4c 1.2.5.10 能生成 BMv2 JSON，使用这些元素时却可能生成 `simple_switch` 无法加载的报头赋值参数。实际运行时可改为逐个元素初始化，以下写法已在本机验证：

```p4
Pair_h[3] pairs;
pairs[0].setValid();
pairs[0].first = 0;
pairs[0].second = 1;
pairs[1].setValid();
pairs[1].first = 2;
pairs[1].second = 3;
```

第三个元素保持无效。这个限制来自当前编译器与目标的组合，不应改写成“P4 禁止报头栈初始化”。

## 5.10 报头联合体 `header_union`

报头联合体表达“这些报头中至多一个有效”。每个成员必须是报头类型；这种互斥关系可以帮助编译器安排存储，但语言不保证成员一定共享某段物理内存。

下面的简化类型只用于展示有效性变化，不代表完整协议报头：

```p4
header Short_h { bit<8> value; }
header Long_h { bit<16> value; }
header_union Alternative_h {
    Short_h shortValue;
    Long_h longValue;
}
```

### 5.10.1 有效性变化

```p4
Alternative_h alternative;           // 两个成员都无效
alternative.shortValue = { 7 };      // shortValue 有效
alternative.longValue = { 300 };     // longValue 有效，shortValue 无效
```

将一个有效报头整体赋给成员，或者对该成员调用 `setValid()`，会使其他成员无效。向成员内部的某个字段赋值，不具有同样的效果。例如，`alternative.shortValue.value = 8` 不会自动切换有效成员。

尤其不要写入当前无效成员的字段：规范允许这种写入影响联合体中另一个有效成员的数据。这也是不能把联合体当作多个独立报头随意写入的原因。

`alternative.isValid()` 在存在有效成员时返回 `true`。联合体自身没有 `setValid()`、`setInvalid()` 方法，应通过成员报头管理有效性；同类型联合体之间也可以整体复制。`emit` 一个联合体时，只输出其中当前有效的成员；全部无效则不输出。

### 5.10.2 用于 Parser 的协议分支

在完整程序中，可以将已声明的 `IPv4_h`、`IPv6_h` 组合为联合体，再与以太网报头一起放入结构体：

```p4
header_union IP_h {
    IPv4_h v4;
    IPv6_h v6;
}
struct Parsed_packet {
    Ethernet_h ethernet;
    IP_h ip;
}
```

Parser 中先提取以太网报头，再按 EtherType 选择成员：

```p4
parser ParseIP(packet_in packet, out Parsed_packet hdr) {
    state start {
        packet.extract(hdr.ethernet);
        transition select(hdr.ethernet.etherType) {
            0x0800: parse_ipv4;
            0x86DD: parse_ipv6;
            default: accept;
        }
    }
    state parse_ipv4 {
        packet.extract(hdr.ip.v4);
        transition accept;
    }
    state parse_ipv6 {
        packet.extract(hdr.ip.v6);
        transition accept;
    }
}
```

这里假设两个 IP 报头都是已定义的定长类型。未知 EtherType 按示例策略结束解析，两个 IP 成员保持无效；若省略 `default`，规范要求无匹配分支时以 `error.NoMatch` 拒绝解析，本机 BMv2 的实现差异及处理方法见 [6.4.1 节](./06-Parser解析器.md#641-select-表达式)。`accept` 只表示解析结束，后续转发策略由控制块决定。

## 5.11 `struct`

`struct` 按名字组织字段，自身没有有效位。常见用途是汇集解析得到的报头，或在各处理块之间传递元数据：

```p4
struct Metadata {
    bit<9> ingressPort;
    bit<16> l4SourcePort;
    bool multicast;
}
```

结构体可以包含整数、`bool`、`error`、枚举、报头、报头联合体、报头栈、其他结构体和元组等，但不是任意类型都能作为字段。任意精度 `int`、`string`、`void`、`match_kind`、`list` 以及 extern、Parser、Control、Package 对象都不能直接作为结构体字段。

同类型结构体可以整体赋值。如果所有成员都可比较，还可以逐字段进行相等／不等比较。初始化支持按顺序或按字段名填写；未填写的字段要么补齐，要么使用 5.18 节的 `...`。`{#}` 不是结构体的无效值，含报头的结构体由各个报头分别保存有效性。

## 5.12 `tuple`

元组把若干值组合起来，各元素可以有不同类型，用下标而不是字段名访问：

```p4
tuple<bit<32>, bool, bit<16>> fields = { 10, false, 80 };
bit<16> port = fields[2];
fields = { 20, true, 443 };
```

下标必须在局部编译期已知，这样编译器才能确定访问结果的类型。v1.2.5 将元组元素访问规定为非左值，因此本章用整体赋值更新元组；本机 p4c 也接受单独修改元素的写法，但不应据此改写所采用版本的规则。

裸的 `{ f1, f2 }` 是元组表达式，还可用于初始化结构体、报头，或给 extern 传入一组值。V1Model 的 `hash` 数据参数常使用这种形式；它不是 `list<T>`。

## 5.13 `list`

`list<T>` 的所有元素类型相同，列表值使用带类型的表达式 `(list<T>){ ... }`。例如，架构可以声明一个接收编译期配置列表的 extern：

```p4
extern Choices {
    Choices(list<bit<8>> values);
    void apply();
}
control UseChoices() {
    Choices((list<bit<8>>){ 1, 2, 3 }) choices;
    apply {
        choices.apply();
    }
}
```

这是接口示意，目标需要提供 `Choices` 的实现，不能直接当作 BMv2 已有功能使用。列表也不是可以在数据平面随意增删元素的通用动态数组。

Parser `select` 标签中的 `8w1 .. 8w3` 表示范围集合；编译器使用内部的集合类型检查它，不能把 `list` 与这类集合表达式混为一谈。

## 5.14 可序列化枚举与未命名编码

沿用 5.7 节的 `EtherType`，可以把它用于报头字段：

```p4
header TypedEthernet_h {
    bit<48> dstAddr;
    bit<48> srcAddr;
    EtherType etherType;
}
```

底层类型决定字段的线上位宽，本例仍是 16 位。**枚举成员列表不自动构成输入校验。** 报文里的任意 16 位编码都可以被提取到该字段，包括没有命名的值；程序仍须用 `select`、`if` 或 `verify` 实现所需策略。

显式转换也可以产生未命名编码：

```p4
EtherType unknown = (EtherType)16w0xFFFF;
bool known = unknown == EtherType.IPV4 ||
             unknown == EtherType.ARP ||
             unknown == EtherType.IPV6; // false
```

因此，不应假设某个可序列化枚举值总能命中已列出的成员。普通枚举则没有程序员指定的线上整数表示，不能放入报头字段。

## 5.15 `extern`

extern 对象与 extern 函数声明外部接口，实现由架构和目标提供。计数器、寄存器、报文输入输出通常以 extern 对象提供，哈希等功能也可能以 extern 函数提供。

extern 对象通过实例化创建，不能像普通整数或结构体那样赋值复制。调用者只能使用接口允许的构造函数和方法。详见 [第 12 章](./12-外部对象Extern.md)。

## 5.16 `parser` / `control` / `package` 类型

这三类类型与普通数据类型的用途不同：

| 类型      | 作用                                        |
| --------- | ------------------------------------------- |
| `parser`  | 声明解析接口，并可用状态机给出 P4 实现      |
| `control` | 声明处理接口，并可用 `apply` 块给出 P4 实现 |
| `package` | 声明架构组合接口，通过构造参数装配各组件    |

Parser 和 Control 实例可通过 `apply` 调用，架构也会调用它规定的顶层处理块。Package 没有普通的 P4 `apply` 实现体，其组件如何调度由架构规定。不能把三者都理解为“加一个代码块就能实现的函数”。相关内容见 [第 6 章](./06-Parser解析器.md)、[第 7 章](./07-控制块与动作.md)和 [第 10 章](./10-架构与包.md)。

## 5.17 默认值与未初始化值

**类型有默认值，不等于省略初始化就会使用该值。** 例如，`bit<8> x;` 不保证 x 为 0，`bool b;` 不保证 b 为 `false`。显式写入值，或者使用下一节的 `...`，才能要求默认初始化。

局部报头、联合体及报头栈有专门的有效性初始化规则。结构体中包含这些类型时，也会递归初始化其有效性，但普通整数和布尔字段不会因此一并清零。`out` 参数也遵守相应的初始化规则，见 [4.8 节](./04-语法基础.md#48-参数方向修饰符)。

下表描述显式请求默认值时的结果：

| 类型                      | 默认值                                   |
| ------------------------- | ---------------------------------------- |
| `bit<W>`、`int<W>`、`int` | 0                                        |
| `bool`                    | `false`                                  |
| `error`                   | `error.NoError`                          |
| `string`                  | 空字符串                                 |
| `varbit<W>`               | 长度为 0 的位串，不是 W 个零比特         |
| 有底层类型的枚举          | 底层编码 0，即使没有成员命名为 0         |
| 无底层类型的枚举          | 声明中的第一个成员                       |
| `header`                  | 无效报头                                 |
| `header_union`            | 所有成员无效                             |
| 报头栈                    | 所有元素无效，解析索引为 0               |
| `struct`、`tuple`         | 各成员分别取默认值，前提是这些默认值存在 |

这张表不表示每种类型都能声明普通运行时变量。`match_kind`、函数类型、集合类型、extern、Parser、Control、Package 等没有这样的默认值。

## 5.18 用 `...` 做默认初始化

下面先声明供示例使用的类型：

```p4
struct Settings {
    bit<32> count;
    bool enabled;
}
enum bit<8> WireKind { One = 1, Two = 2 }
enum State { Idle, Busy }
```

在执行位置显式请求默认值：

```p4
bit<8> number = ...;                // 0
WireKind kind = ...;                // 底层编码 0，没有对应的命名成员
State state = ...;                  // State.Idle
Settings first = { 1, ... };        // count = 1，enabled = false
Settings second = { enabled = true, ... }; // count = 0，enabled = true
```

`...` 表示为未明确填写的成员使用默认值，必须放在初始化表达式的最后。`{ ..., enabled = true }` 是故意列出的错误写法，不能使用。

对报头，要区分整个对象的默认值与字段的默认值：

```p4
Pair_h invalidPair = ...;                // 无效报头
Pair_h validPair = { second = 5, ... }; // 有效，first = 0，second = 5
Pair_h zeroPair = { ... };               // 有效，两个字段都为 0
```

`Pair_h` 沿用 5.8.4 节的声明。`= ...` 得到报头类型的默认值，即无效报头；`= { ... }` 则构造一个已填入默认字段值的有效报头。两者不能互换。

## 5.19 `typedef` 与 `type`

`typedef` 为已有类型起别名；`type` 创建与原类型不同的新类型：

```p4
typedef bit<32> IPv4Addr;
type bit<32> NodeId;
type bit<32> PortId;
```

`IPv4Addr` 与 `bit<32>` 是同一类型。`NodeId`、`PortId` 则彼此不同，也不同于底层的 `bit<32>`：

```p4
IPv4Addr address = 32w0xC0000201;
bit<32> rawAddress = address;
bit<32> rawId = 7;
NodeId node = (NodeId)rawId;
bit<32> restored = (bit<32>)node;
```

`type` 支持以固定位宽整数、`bool`，或由这些类型派生的新类型为基础；它不能像 `typedef` 那样为任意报头或结构体建立别名。新类型也不自动获得底层整数的全部算术运算，计算时需先转回底层类型。

这种区分可以让编译器发现把已有 `NodeId` 值直接赋给 `PortId` 的错误，但显式转换仍可能改变数值含义，不能代替业务逻辑校验。

## 5.20 本章小结

检查类型使用时，需要分别回答三个问题：值的表示和允许的操作是什么；值是否已经初始化；如果它是报头，当前是否有效。报头栈的解析索引和联合体的成员互斥性还带有额外语义，不能只按普通数组或结构体理解。

本章涉及的目标限制仍须通过后端编译和报文实验确认。尤其不要把一次无效字段读取的观测结果，当作语言对所有实现的保证。
