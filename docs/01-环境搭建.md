# 01 · 环境搭建

本章以 Ubuntu 24.04 为基础，准备 P4 编译器、BMv2 软件交换机和 Mininet，并分别检查编译、报文处理和虚拟网络是否正常。已有 P4 环境的读者可以直接从 [1.4 环境自检](#14-环境自检) 开始。

## 1.1 需要哪些组件

本教程的主要实验采用 **P4<sub>16</sub> + V1Model + BMv2**。P4<sub>16</sub> 是语言，V1Model 定义程序与目标之间的接口，BMv2 的 `simple_switch` 则实现这一架构。

| 组件                               | 在实验中的作用                                                         |
| ---------------------------------- | ---------------------------------------------------------------------- |
| `p4c` / `p4c-bm2-ss`               | 将 P4 源码编译为 BMv2 能加载的 JSON，也可生成描述控制平面接口的 P4Info |
| `p4test`                           | 检查语言与类型规则，VSS 参考示例使用它做静态检查                       |
| `core.p4` / `v1model.p4`           | 编译时使用的核心库与架构声明，随 p4c 安装                              |
| `simple_switch`                    | 执行编译后的程序，通过 Thrift 接口接受配置                             |
| `simple_switch_CLI`                | 连接 Thrift 接口，配置表项、多播组等                                   |
| `simple_switch_grpc`               | 提供 P4Runtime 服务端接口，供控制平面章节使用                          |
| Mininet                            | 用 Linux 网络命名空间和虚拟链路组织实验拓扑                            |
| `ip`、`ping`、`tcpdump`、`ethtool` | 创建接口、检查连通性、抓包及调整网卡卸载功能                           |

`simple_switch` 提供 Thrift 控制接口，`simple_switch_grpc` 提供 P4Runtime 服务，是否同时支持 Thrift 取决于构建配置。安装了前者不意味着后者也已可用，工具用途见 [14.1 节](./14-BMv2编译与运行.md#141-工具链与编译产物)。

仓库中编号为 `01` 至 `05` 的示例，目前由 `run.sh` 直接创建 network namespace 与 veth，没有调用 Mininet。两种方式都能构造虚拟网络，但启动步骤不能混用。

## 1.2 本章的验证环境

以下是本次自检使用的环境，供复现时对照，不是各组件的最低版本要求。

| 项目     | 实测值                                         |
| -------- | ---------------------------------------------- |
| 核验日期 | 2026-09-27                                     |
| 操作系统 | Ubuntu 24.04.5 LTS，x86_64                     |
| 运行环境 | WSL2，Linux `6.6.87.2-microsoft-standard-WSL2` |

| BMv2     | `1.15.0-2bdd0b7b`                              |

这里的“原生安装”指工具装在 Ubuntu 用户空间内，不使用 Docker。已在上述环境验证 Hello P4 编译、BMv2 报文反射和 Mininet 两主机直连；本次没有在空白系统中重新执行完整安装流程，也没有验证 Docker 路线。

在其他主机或虚拟机上复现时，记录 `uname -r` 和工具版本，并重新执行自检。WSL2 的一次成功运行不能替代对其他内核与网络配置的验证。

## 1.3 安装工具链

### 1.3.1 Ubuntu 24.04 安装路径

需要从头安装时，可以使用 Andy Fingerhut 维护的 [p4-guide 安装说明](https://github.com/jafingerhut/p4-guide/blob/master/bin/README-install-troubleshooting.md)。其中的 `install-p4dev-v8.sh` 支持 Ubuntu 24.04，会安装或构建 P4 工具链，并为 Python 依赖建立虚拟环境。脚本应由普通用户启动，需要系统权限的步骤会调用 `sudo`。

建议在专用的 Ubuntu 系统或虚拟机中安装。上游安装说明要求至少 2 GB 内存、建议 4 GB，并预留至少 25 GB 可用磁盘空间；编译耗时和内存占用还取决于并行度与源码版本。安装前先检查：

```bash
cat /etc/os-release
uname -m
free -h
df -h .
```

以下命令使用 Bash，在独立工作目录中运行。不要在本教程仓库内构建整套工具链。

```bash
sudo apt update
sudo apt install -y git

mkdir -p "$HOME/p4-work"
cd "$HOME/p4-work"
git clone https://github.com/jafingerhut/p4-guide.git
git -C p4-guide rev-parse HEAD | tee p4-guide-revision.txt

set -o pipefail
./p4-guide/bin/install-p4dev-v8.sh |& tee install.log
```

`pipefail` 使安装脚本失败时整个管道也返回失败，避免 `tee` 的成功掩盖前面的错误。失败后应先查 `install.log` 中实际失败的命令，再决定修复或重试。

脚本把源码目录、Python 虚拟环境和 `p4setup.bash` 放在**启动脚本时的工作目录**。按上述路径安装后，在需要使用工具链的终端执行：

```bash
source "$HOME/p4-work/p4setup.bash"
```

如果安装时使用了其他目录，应调整该路径。脚本更新后安装的组件版本可能变化，因此应保留安装日志，并在安装完成后记录实际版本。[脚本源码](https://github.com/jafingerhut/p4-guide/blob/master/bin/install-p4dev-v8.sh)是核对其行为的直接依据。

现有环境若只缺少实验辅助工具，可按需从 Ubuntu 仓库安装：

```bash
sudo apt install -y iproute2 iputils-ping tcpdump ethtool
```

若未通过上游脚本安装 Mininet，也可安装 Ubuntu 的 `mininet` 包。先检查已有的 `mn` 路径和 Python 模块，避免在不清楚来源的情况下混用两套安装。

### 1.3.2 其他安装方式

| 路线                     | 使用前需要核对的内容                                                                                                                                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ubuntu / Debian 二进制包 | 按 [p4c 安装说明](https://github.com/p4lang/p4c#installing-packaged-versions-of-p4c)选择与发行版匹配的软件源。其使用的是 openSUSE Build Service 仓库，不是 Launchpad PPA；p4c 包本身不等于完整实验环境            |
| Docker                   | 分别核对 [p4c 镜像说明](https://github.com/p4lang/p4c#docker)与 [p4app 使用说明](https://github.com/p4lang/p4app)。不要根据镜像名称推断它包含 Mininet、P4Runtime 服务端及全部 Python 依赖；记录所用标签和镜像摘要 |
| 预装虚拟机               | [p4-guide](https://github.com/jafingerhut/p4-guide/blob/master/bin/README-install-troubleshooting.md)提供虚拟机镜像及适用平台说明，启动后仍应运行本章自检                                                         |

容器中的网络实验还依赖宿主机内核、网络命名空间和相应权限。单独运行 p4c 编译程序，与在容器中创建链路、抓取报文的权限要求不同。

### 1.3.3 Python 解释器与依赖

先确认当前终端使用哪个解释器：

```bash
command -v python3
python3 -c 'import sys; print(sys.executable)'
python3 -m pip --version
```

系统 Python 与虚拟环境拥有各自的包目录。普通用户下可以导入某个模块，不代表 `sudo python3` 也可以，因为后者可能选择了另一解释器。

`check-env.sh` 和编号示例的数据平面验证都只使用 Python 标准库，不需要 Scapy。各验证程序的运行方式不同：

| 入口                               | Python 要求与用途                                                |
| ---------------------------------- | ---------------------------------------------------------------- |
| `check-env.sh`                     | 在命名空间内启动 Python，验证一帧报文反射，不调用 `os.setns`     |
| 示例 01、02、03、05 的 `verify.py` | Linux Python 3.12+，通过 `os.setns` 在各主机命名空间中创建套接字 |
| 示例 04 的 `verify.py`             | Python 3.10+，生成 PCAP 并通过 BMv2 文件端口核对报文和计数器     |

因此，基础自检通过后，运行编号示例仍需核对 Python 版本。完整命令依赖见[示例总览](../examples/README.md#运行前)。Mininet 检查另需 `mininet` 模块，P4Runtime 客户端另需 `grpc`、`google.protobuf` 和 P4Runtime 生成的 Python 模块。准备控制平面实验时，在对应虚拟环境中检查：

```bash
python3 - <<'PY'
import sys
import grpc
import google.protobuf
from p4.v1 import p4runtime_pb2, p4runtime_pb2_grpc
from p4.config.v1 import p4info_pb2

print("Python:", sys.executable)
print("grpc:", grpc.__version__)
print("protobuf:", google.protobuf.__version__)
print("P4Runtime 模块导入成功")
PY
```

本次检查中，已有虚拟环境的 `grpcio 1.59.3`、`protobuf 4.21.12` 与所装 P4Runtime 生成代码直接配合时，出现 `Descriptors cannot ... be created directly` 错误。这是生成代码与 protobuf 运行时的兼容问题，不能仅凭“包已安装”判定依赖正常。Protobuf 的相关变更见[上游说明](https://protobuf.dev/news/2022-05-06/)。

对于这一具体组合，以下兼容方式已通过导入检查：

```bash
PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python python3 - <<'PY'
import grpc
import google.protobuf
from p4.v1 import p4runtime_pb2, p4runtime_pb2_grpc
from p4.config.v1 import p4info_pb2

print("P4Runtime 模块导入成功（Python protobuf 实现）")
PY
```

该变量仅对这次命令生效，使用纯 Python protobuf 实现可能降低性能。其他版本组合应按实际报错检查依赖。导入成功只说明客户端模块可以加载，P4Runtime 仲裁、流水线配置与表项读写见[第 15 章](./15-P4Runtime控制平面.md)。

## 1.4 环境自检

以下命令均从**本教程仓库根目录**执行。编译成功、报文处理正确与 Mininet 可用是三个独立的检查结果。

### 1.4.1 命令与版本

```bash
for tool in p4c p4c-bm2-ss p4test simple_switch simple_switch_CLI python3 timeout mn ip ping tcpdump ethtool; do
    command -v "$tool" || printf '未找到：%s\n' "$tool"
done

p4c --version
simple_switch --version
python3 --version
mn --version
```

这里不使用 `simple_switch_CLI --version`；检查 Python 客户端能否启动可用 `simple_switch_CLI --help`。P4Runtime 章节还需要单独检查 `command -v simple_switch_grpc`。

### 1.4.2 编译最小程序

直接使用仓库的 [Hello P4 源码](../examples/01-hello/hello.p4)，编译产物放入临时目录：

```bash
(
    set -e
    check_dir=$(mktemp -d /tmp/p4-compile.XXXXXX)
    trap 'rm -rf -- "$check_dir"' EXIT

    p4c-bm2-ss --std p4-16 --target bmv2 --arch v1model \
        -o "$check_dir/hello.json" \
        --p4runtime-files "$check_dir/hello.p4info.txtpb" \
        examples/01-hello/hello.p4

    test -s "$check_dir/hello.json"
    test -s "$check_dir/hello.p4info.txtpb"
    echo "编译通过，已生成 BMv2 JSON 和 P4Info"
)
```

本机 p4c 支持 `.txtpb` 文本格式；使用 `.txt` 会给出弃用警告。成功生成产物说明编译器能够找到核心库与架构声明，并完成本例的编译，尚未证明交换机能处理报文。

### 1.4.3 验证 BMv2 报文反射

运行仓库提供的[自检脚本](../examples/check-env.sh)：

```bash
sudo bash examples/check-env.sh
```

脚本创建一个独立网络命名空间，用一对 veth 连接测试主机与 BMv2 的端口 1，再加载 Hello P4。该程序将出端口设置为入端口，使收到的报文原路返回。

验证时先打开接收套接字，再发送一帧带随机标识的 60 字节以太帧（不含 FCS），排除本机发包记录后，比较接收到的完整帧。输出中的 `TX` 与 `RX` 十六进制内容应完全一致，并出现：

```text
PASS：Hello P4 编译成功，已生成 BMv2 JSON 和 P4Info
...
PASS：接收方向捕获到逐字节一致的反射帧
PASS：BMv2 报文反射自检完成；退出时清理本次创建的资源
```

脚本在失败时返回非零状态并输出诊断信息；正常结束、报错，或收到 SIGINT、SIGTERM 时，都会清理本次创建的进程、命名空间、接口和临时文件。它不需要控制平面下发表项，也不依赖 Scapy。

仅观察到 ping 不通，无法证明反射成功：ARP 解析失败、链路未启动或程序丢包，都可能产生同样现象。

### 1.4.4 验证 Mininet 基础网络

先用 `python3 -c 'import mininet; print(mininet.__file__)'` 确认当前解释器能导入 Mininet。下面将该解释器的路径明确传给 `sudo`，创建两台直连主机：

```bash
sudo "$(command -v python3)" - <<'PY'
import os
from mininet.net import Mininet
from mininet.log import setLogLevel

setLogLevel("info")
net = Mininet(controller=None, build=False)
tag = f"m{os.getpid()}"
try:
    h1 = net.addHost(tag + "a", ip="10.254.0.1/30")
    h2 = net.addHost(tag + "b", ip="10.254.0.2/30")
    net.addLink(h1, h2)
    net.start()
    loss = net.pingAll(timeout="2")
    if loss != 0:
        raise SystemExit("FAIL：Mininet 直连测试存在丢包")
    print("PASS：Mininet 两主机直连，丢包率 0%")
finally:
    net.stop()
PY
```

此测试验证 Mininet 创建主机、链路及执行命令的能力，拓扑中没有 P4 交换机。`mn --test pingall` 等常规测试同样不能替代 BMv2 验证。将 BMv2 接入 Mininet 的完整脚本见 [14.4.2 节](./14-BMv2编译与运行.md#1442-用-mininet-管理同一拓扑)。

## 1.5 常见问题的定位顺序

| 现象                             | 优先检查                                                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 找不到 `p4c` 或 `simple_switch`  | 用 `command -v` 检查路径；按实际安装位置加载 `p4setup.bash`                                                |
| 找不到 `core.p4` 或 `v1model.p4` | 检查当前 p4c 对应的头文件是否安装。源码安装常见位置为 `/usr/local/share/p4c/p4include`，以实际安装前缀为准 |
| `ModuleNotFoundError`            | 检查 `sys.executable` 与包所在环境，不要只检查另一个终端中的 `pip list`                                    |
| protobuf 的 descriptor 错误      | 核对生成代码与运行时版本，参照 1.3.3 的具体兼容性检查                                                      |
| `Operation not permitted`        | 确认网络命名空间、veth 与原始套接字所需权限；容器内的 root 仍可能受能力限制                                |
| BMv2 无法启动                    | 查看自检输出的日志，检查 JSON、接口及动态库；其他实验还需检查监听端口是否冲突                              |
| 编译通过但收不到反射帧           | 检查 BMv2 是否存活、端口是否绑定正确、接口是否启用，以及抓包是否区分收发方向                               |
| Mininet 导入成功但连通性失败     | 查看主机、接口与 ping 输出；导入模块本身不能验证网络功能                                                   |

保留失败命令与日志，逐层定位。不要把重装工具链作为所有问题的第一步。

## 1.6 仓库目录与日常使用

目前的目录结构如下，`runtime/` 按示例需要提供：

```text
examples/
├── check-env.sh               # 编译与 BMv2 报文反射自检
├── 01-hello/
│   ├── README.md
│   ├── hello.p4
│   ├── build.sh
│   ├── run.sh                # network namespace + veth
│   └── verify.py             # 两端口逐帧反射验证
├── 02-l2-switch/             # 其余编号示例采用相似结构
│   ├── README.md
│   ├── l2_switch.p4
│   ├── build.sh
│   ├── run.sh
│   ├── verify.py
│   └── runtime/
│       └── s1-commands.txt   # Thrift CLI 命令
├── 03-ipv4-router/
├── 04-acl/
├── 05-ecmp/                  # runtime/ 中另有 P4Runtime 客户端
└── vss/                     # 架构阅读与静态检查，无配套运行目标
```

各编号示例的 `build.sh` 默认将产物写入示例目录，也可用第一个参数指定输出目录。`run.sh` 需要网络管理权限，每次都会将当前源码重新编译到临时目录，不必先执行 `build.sh`。它还会调用 `verify.py`，退出时清理本次创建的资源。

运行前阅读对应 README。需要保留拓扑时使用 `--keep`，并在退出前复制需要保存的日志。编辑器可自行选择，语言插件的诊断不能代替 p4c 编译与目标上的运行验证。
