# 13 · 注解与高级特性

本章依据 [P4₁₆ 1.2.5 规范](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html)，说明注解、静态断言、泛型、构造参数及 Parser 值集合。涉及目标行为的结论使用 p4c 1.2.5.10（`8b6de3c57`）和 BMv2 `simple_switch` 1.15.0-2bdd0b7b 验证。

独立的语言示例可用 `p4test --std p4-16 文件名.p4` 检查。引用 `hdr`、`meta`、`sm` 的片段需要放入相应处理块，13.7 节提供完整的 V1Model 程序及编译命令。

## 13.1 注解的两种形式

注解以 `@` 开头，附着在语言允许的位置，如声明、字段、参数或块语句前。注解的名称和主体共同表达信息，具体语义由语言规范、架构或工具定义。

### 13.1.1 非结构化与结构化注解

```p4
@note
const bit<8> A = 1;

@note("reviewed", 2)
const bit<8> B = 2;

@info[owner="network", revision=2]
const bit<8> C = 3;
```

非结构化注解可以只有名称，也可以带圆括号主体。结构化注解必须带方括号，允许空主体 `@info[]`。具体注解按其定义选择形式，例如规范中的 `@name("routes")` 使用圆括号内的字符串主体。

### 13.1.2 同一元素上的命名规则

| 同一元素上的组合               | 规范规则                               |
| ------------------------------ | -------------------------------------- |
| 多个同名非结构化注解           | 通用语法允许，仍须满足该注解自身的限制 |
| 多个同名结构化注解             | 不允许                                 |
| 同名的结构化与非结构化注解并用 | 不允许                                 |

这些限制分别作用于每个被注解的元素。`@name` 等预定义注解还有更严格的数量和组合约束，见 13.2.1 节。

### 13.1.3 非结构化注解的主体

主体由词法记号组成，内部圆括号必须配对。具体注解可以进一步要求字符串、表达式或其他格式，例如 `@deprecated` 要求字符串消息，`@atomic` 则没有主体。

自定义注解的用途和输出形式由使用它的工具约定，需要与相应工具配套使用。

### 13.1.4 结构化注解的主体

主体可以是空列表、表达式列表或键值列表，不能混用后两者：

```p4
@Empty[]
@Values[1, "hello", true, 1 == 2, 5 + 6]
@Labels[short="L1", long="Label One"]
const bit<8> MARK = 0;
```

所有值必须在编译期已知，类型只能是 `string`、任意精度 `int` 或 `bool`。这里的 `1` 是 `int`，而 `8w1` 是 `bit<8>`，不能直接放入结构化注解。P4Info 等输出格式还可能进一步限制整数范围。

下面三个独立示例分别展示不合法的主体形式、重复键和类型：

```p4
@Mixed[key=4, 5]                 // 错误：键值与位置表达式混用
const bit<8> BAD_MIX = 0;

@Labels[k=1, k=2]                // 错误：同一主体内键名重复
const bit<8> BAD_KEY = 0;

@Sized[8w1]                     // 错误：值的类型是 bit<8>
const bit<8> BAD_TYPE = 0;
```

## 13.2 常用预定义注解

| 注解                         | 作用与限制                                          |
| ---------------------------- | --------------------------------------------------- |
| `@name("...")`               | 指定控制平面名称，可影响局部名或使用绝对路径        |
| `@hidden`                    | 从生成的控制平面 API 中隐藏实体，具体接口支持须核实 |
| `@atomic`                    | 要求一段代码原子执行，目标必须具备相应能力          |
| `@optional`                  | 允许省略规范指定接口上的参数，不限于构造参数        |
| `@tableonly`、`@defaultonly` | 限制表动作列表中的动作用于普通表项或默认动作        |
| `@deprecated("消息")`        | 使用被弃用的构造时产生诊断                          |
| `@noWarn("类别")`            | 请求抑制指定类别的警告，类别名和适用范围取决于工具  |
| `@match(kind)`               | 指定 `value_set` 元素结构中某字段的匹配种类         |
| `@pure`、`@noSideEffects`    | 描述 extern 函数／方法的状态依赖和副作用            |

### 13.2.1 `@name`：控制平面名称

控制平面名称由实体局部名与包含它的实例路径构成。源码名、控制平面全名和 P4Info 中的别名各有用途，控制器通过编译产物确认名称和 ID。

以 13.7 节的程序为基础，在 `MyIngress` 声明区加入下面的表，并在 `apply` 中调用 `t.apply()`：

```p4
@name("routes")
table t {
    key = { hdr.ethernet.etherType: exact; }
    actions = { NoAction; }
    size = 16;
    const default_action = NoAction();
}
```

本机生成的表名为 `MyIngress.routes`，P4Info 别名为 `routes`。P4 源码中仍使用原标识符，通过 `t.apply()` 调用该表。

| 标注               | 本机示例中的控制平面表名 |
| ------------------ | ------------------------ |
| 不标注             | `MyIngress.t`            |
| `@name("routes")`  | `MyIngress.routes`       |
| `@name(".routes")` | `routes`                 |

前导点表示绝对路径，生成的名称不保留该点。使用绝对路径时，各实例中的可控对象仍须具有全局唯一的控制平面名称。

规范要求同一元素在 `@name` 与 `@hidden` 之间合计最多出现一次，每个控制平面名称最多指向一个可控实体。本机测试中，部分重复 `@name` 或与 `@hidden` 并用的写法未被拒绝，书写时仍应遵守这项规范约束。

### 13.2.2 `@hidden`：区分控制接口

把上一节表前的注解换为 `@hidden`，本机生成的 P4Info 中不再列出该表。BMv2 JSON 仍保留它，表在数据平面中照常执行，也可通过 Thrift CLI 找到并配置。

### 13.2.3 `@atomic`：共享状态的原子操作

以 V1Model 为例，在 Control 声明区定义 `register<bit<32>>(1024) pkt_count;`。下面动作要求 `meta.index` 为已初始化且小于 1024 的 `bit<32>`：

```p4
action increment_count() {
    bit<32> value;
    @atomic {
        pkt_count.read(value, meta.index);
        value = value + 1;
        pkt_count.write(meta.index, value);
    }
}
```

单次 extern 方法调用具有原子性，这里的 `@atomic` 将保护范围扩大到整个读、改、写序列，避免并发报文更新同一状态时丢失修改。

规范要求后端实现所标注范围的原子执行，无法实现时应拒绝程序。本机 BMv2 在单个动作内锁住所访问的寄存器数组，跨动作范围的实现情况与验证见 [12.6.2 节](./12-外部对象Extern.md#1262-原子性与-bmv2-的实现边界)。

### 13.2.4 `@tableonly` 与 `@defaultonly`

这两个注解写在表的 `actions` 列表元素前，分别限定该动作在本表中用于普通表项或默认动作。动作在其他位置的直接调用按普通调用规则处理，完整示例见 [8.5.2 节](./08-匹配动作表.md#852-tableonly-和-defaultonly)。

### 13.2.5 `@deprecated`

```p4
@deprecated("Use identity_new instead")
bit<16> identity_old(in bit<16> value) {
    return value;
}
```

在可达的调用位置使用 `identity_old`，本机 p4c 会报告 `deprecated` 警告并附带消息。编译器选项可进一步抑制该类警告或将其提升为错误。

### 13.2.6 `@noWarn`

`@noWarn` 请求抑制指定类别的警告，类别名由工具定义。例如，本机重复优先级诊断的类别名为 `duplicate-priorities`。

下面是放在 Parser 声明区的示例：

```p4
@noWarn("unused")
value_set<bit<16>>(8) reserved_types;
```

注解的作用范围由编译器的相应检查决定。需要配置整个编译过程时，p4c 还提供 `--Wdisable=unused`、`--Werror=deprecated` 等选项，前者抑制对应诊断，后者将对应警告视为错误。

### 13.2.7 `@optional`

规范允许它用于 Package、Parser 类型、Control 类型的参数，以及 extern 方法、函数和对象构造参数。普通用户函数和动作省略实参时，使用 13.6 节所述的默认值规则。

下面是可独立交给 `p4test` 的 Package 示例：

```p4
package Pipeline();
package Switch(Pipeline first, @optional Pipeline second);
Pipeline() ingress;
Switch(ingress) main;
```

省略 `second` 后的含义由架构规定，默认值与可选参数的组合规则见 13.6 节。

### 13.2.8 `@match(kind)`

需要指定非精确匹配时，注解写在 `value_set` 元素结构的字段上，即使只匹配一个字段也应使用结构体：

```p4
struct etype_key_t {
    @match(ternary)
    bit<16> etherType;
}
```

类型声明放在程序全局，Parser 内再声明 `value_set<etype_key_t>(8) allowed_etypes;`。`@match` 以结构字段为单位指定匹配种类，未标注的字段默认使用 `exact`。

本机 BMv2 后端只支持值集合的精确匹配。上述 `ternary` 字段会触发 `unsupported` 警告，生成的 BMv2 JSON 忽略其非精确匹配注解，P4Info 中却仍标为 `TERNARY`。13.7 节采用 `bit<16>` 精确匹配集合。

### 13.2.9 `@pure` 与 `@noSideEffects`

`@pure` 表示 extern 函数／方法只依赖 `in` 实参，不读写隐藏状态，影响限于返回值及输出参数。`@noSideEffects` 较弱：不改变隐藏状态，但可以读取它，例如寄存器的 `read`。

这类注解应由接口提供者按 extern 的实际语义标注，编译器将其作为消除无用调用等优化的依据。

## 13.3 `static_assert`：检查编译期条件

核心库提供两个重载，程序通过 `core.p4` 引入：

```p4
extern bool static_assert(bool check, string message);
extern bool static_assert(bool check);
```

参数没有方向修饰符，条件和消息必须在编译期已知。条件为真时返回 `true`，为假时产生编译错误，并在提供消息时报告该消息。

### 13.3.1 配置检查

下面是完整的语言检查示例：

```p4
#include <core.p4>
const bit<32> BUCKETS = 8;
const bool BUCKETS_OK = static_assert(
    BUCKETS > 0 && BUCKETS <= 1024,
    "BUCKETS must be in 1..1024");
```

顶层不允许直接放调用语句，所以这里用返回值初始化常量。将 `BUCKETS` 改为 0 时，编译器会报告断言失败。

也可以在条件中检查 `V1MODEL_VERSION`，约束程序采用的接口分支。

### 13.3.2 布局检查的范围

在 13.7 节程序的 Control 中，可以写：

```p4
static_assert(hdr.ethernet.minSizeInBits() == 112,
              "Ethernet header must contain 112 bits");
```

尺寸方法依据类型计算，适合检查报头总位宽。字段顺序和线路格式则需结合报头声明与实际输出字节核对。

Parser 的 `verify` 用于运行时的输入检查，与 `static_assert` 的编译期检查配合使用。

## 13.4 泛型：类型参数与具体实现

### 13.4.1 哪些声明可以参数化

| 声明                               | 类型参数的用途                               |
| ---------------------------------- | -------------------------------------------- |
| `extern` 类型、extern 方法和函数   | 使接口适用于不同数据类型                     |
| 普通函数                           | 以类型参数声明形参、返回值或局部值           |
| Parser／Control 类型声明、Package  | 参数化架构接口与装配关系                     |
| `struct`、`header`、`header_union` | 参数化数据结构，报头栈可使用特化后的报头类型 |

例如，以下类型和函数声明放在程序全局：

```p4
struct Cell<T> { T value; }
struct Box<T> { Cell<T> cell; }
header Word<T> { T value; }
header_union Either<T> { Word<T> item; }

T identity<T>(in T value) {
    return value;
}
```

不同类型之间可以嵌套，例如 `Box<bit<16>>` 包含 `Cell<bit<16>>`。本机将 `Cell<Cell<bit<16>>>` 视为递归类型特化并拒绝。特化后的类型仍须满足原构造的规则，例如报头字段必须采用允许放入报头的类型。

### 13.4.2 类型推断与显式特化

使用上一节的 `identity` 时，下列片段可放入 Control 的 `apply`：

```p4
bit<16> first = identity(16w7);
bit<16> second = identity<bit<16>>(16w7);
```

第一行从实参推断类型，第二行显式指定。类型信息不足时，可显式给出类型实参。Extern 和 Package 的类型推断同样依据其声明与实参。

下面的完整 Package 示例可由 `p4test` 检查：

```p4
control Block<T>(out T value);
package Top<T>(Block<T> body);
control MakeValue(out bit<32> value) {
    apply { value = 1; }
}
Top(MakeValue()) main;
```

这里从 `MakeValue` 的接口推断出 `T` 为 `bit<32>`，也可写成 `Top<bit<32>>(MakeValue()) main;`。

### 13.4.3 类型变量上的操作

泛型函数的主体按类型变量检查，下面的加法在一般的 `T` 上没有定义：

```p4
T plus_one<T>(in T value) {
    return value + 1;  // 错误：一般的 T 没有定义加法
}
```

类型变量支持赋值和参数传递。需要加法时，可以采用具体整数类型，或通过具有明确操作语义的 extern 接口实现。

### 13.4.4 Parser／Control 泛型实现的版本差异

规范 v1.2.5 的第 13.2、14 节限制带主体的 Parser／Control 实现不能泛型，第 8.24、15.1 节又给出泛型实现或直接调用示例，两处表述存在不一致。本机 p4c 能接受部分泛型实现。

本教程的可运行主程序使用具体类型的 Parser／Control 实现，架构接口和 Package 则按需要使用泛型。对应说明见 [第 6 章](./06-Parser解析器.md)、[第 7 章](./07-控制块与动作.md)和 [10.10 节](./10-架构与包.md#1010-直接类型调用)。

## 13.5 构造函数调用

Extern、Parser、Control 和 Package 可以通过相应构造形式建立实例，构造表达式在编译期完成实例的装配与参数绑定。

### 13.5.1 构造参数与运行时参数

```p4
control AddStep(inout bit<32> value)(bit<32> step) {
    apply { value = value + step; }
}
control Caller(inout bit<32> value) {
    AddStep(1024) increment;
    apply { increment.apply(value); }
}
```

Parser／Control 声明中的第一组括号是运行时参数，第二组是构造参数，后者必须无方向，实参在编译期确定。`AddStep(1024)` 绑定 `step`，`increment.apply(value)` 则处理本次调用的值。Package 只有构造参数，extern 构造函数由同名方法声明，见 [10.9 节](./10-架构与包.md#109-运行时参数与构造参数)。

### 13.5.2 架构提供的表实现

在 V1Model 中，间接动作表可以使用 `implementation = action_profile(1024);` 这样的构造表达式，其中 `action_profile` 由架构定义。

本机导出 P4Info 时，需为该匿名构造表达式所在的属性命名，例如 `@name("members") implementation = action_profile(1024);`。

`implementation` 属性的语义遵循架构规则，间接表的动作成员由控制平面管理，配置方式见 [第 8 章](./08-匹配动作表.md)。

## 13.6 可选参数与默认值

只有 `in` 和无方向参数允许默认值，默认表达式必须在编译期已知。下面的普通函数放在程序全局：

```p4
bit<8> choose(in bit<8> a, in bit<8> b = 2, in bit<8> c) {
    return a + b + c;
}
```

在调用位置：

```p4
bit<8> x = choose(a = 1, c = 3);  // b 使用默认值，x 为 6
bit<8> y = choose(1, 2, 3);       // 三个位置实参，y 为 6
// choose(1, 3);                 // 错误：3 对应 b，必需的 c 仍缺失
```

省略中间位置的参数时应使用具名实参。同一次调用要么全部使用具名实参，要么全部使用位置实参。

`@optional` 允许省略实参，其含义由接口规定。默认参数则采用声明中给出的默认值，同一个参数不能同时有 `@optional` 和默认值。若参数列表同时含有可选参数和带默认值的参数，调用时必须使用具名实参。完整参数规则见 [4.8 节](./04-语法基础.md#48-参数方向修饰符)，本机混合参数用例见 [10.5.2 节](./10-架构与包.md#1052-默认参数与可选参数)。

## 13.7 `value_set`：由控制平面更新 Parser 匹配集合

本节在 Parser 的局部声明区定义值集合，并在 `select` 中用它选择分支。容量参数在编译期确定，`value_set<bit<16>>(8)` 声明容量为 8、键宽为 16 位的值集合，具体资源分配和容量限制由目标实现。

值集合提供匹配条件，匹配后的解析操作写在所选状态中。多个分支同时符合条件时，Parser 按 `select` 的源码顺序选择第一个匹配分支。

### 13.7.1 完整示例：按 EtherType 放行

将下面程序保存为 `value-set-demo.p4`。集合初始为空，未匹配的报文丢弃，匹配者原样从端口 2 输出。程序只提取 Ethernet 固定报头，其后的字节作为未解析负载保留。

```p4
#include <core.p4>
#include <v1model.p4>

header ethernet_t {
    bit<48> dst;
    bit<48> src;
    bit<16> etherType;
}
struct headers { ethernet_t ethernet; }
struct metadata { bool selected; }

parser MyParser(packet_in packet, out headers hdr,
                inout metadata meta, inout standard_metadata_t sm) {
    value_set<bit<16>>(8) allowed_etypes;
    state start {
        meta.selected = false;
        packet.extract(hdr.ethernet);
        transition select(hdr.ethernet.etherType) {
            allowed_etypes: selected;
            default: accept;
        }
    }
    state selected {
        meta.selected = true;
        transition accept;
    }
}
control MyVerifyChecksum(inout headers hdr, inout metadata meta) {
    apply { }
}
control MyIngress(inout headers hdr, inout metadata meta,
                  inout standard_metadata_t sm) {
    apply {
        if (sm.parser_error != error.NoError || !meta.selected) {
            mark_to_drop(sm);
            exit;
        }
        sm.egress_spec = 2;
    }
}
control MyEgress(inout headers hdr, inout metadata meta,
                 inout standard_metadata_t sm) {
    apply { }
}
control MyComputeChecksum(inout headers hdr, inout metadata meta) {
    apply { }
}
control MyDeparser(packet_out packet, in headers hdr) {
    apply { packet.emit(hdr.ethernet); }
}

V1Switch(MyParser(), MyVerifyChecksum(), MyIngress(), MyEgress(),
         MyComputeChecksum(), MyDeparser()) main;
```

编译并同时生成 P4Info：

```bash
p4test --std p4-16 value-set-demo.p4
p4c-bm2-ss --std p4-16 --arch v1model \
    --p4runtime-files value-set-demo.p4info.json \
    -o value-set-demo.json value-set-demo.p4
```

本机 P4Info 将 `MyParser.allowed_etypes` 描述为大小 8、键宽 16 位的 `EXACT` 值集合。交换机加载程序后，按下一节的 Thrift CLI 命令配置成员。

### 13.7.2 Thrift CLI 配置与验证

本机 BMv2 版本的 `runtime_CLI.py` 在 `parse_pvs_value` 中用 `(bitwidth + 7) / 8` 计算字节数。Python 3 的 `/` 返回浮点数，导致 16 位值被补成 3 字节。交换机要求 2 字节，执行 `pvs_add` 因此触发长度断言并退出。下方兼容入口改用整数除法 `//` 计算长度，并检查输入是否处于无符号字段的取值范围内。

若使用这一版本，可将下面的兼容入口保存为 `pvs-cli.py`。它只替换当前 CLI 进程中的值编码函数，不改动已安装的模块：

```python
import runtime_CLI
import sswitch_CLI


def parse_pvs_value(text, bitwidth):
    try:
        value = int(text, 0)
    except ValueError:
        raise runtime_CLI.UIn_BadParamError("Invalid integer")
    if not 0 <= value < (1 << bitwidth):
        raise runtime_CLI.UIn_BadParamError(
            "Value must fit in an unsigned {}-bit field".format(bitwidth))
    return value.to_bytes((bitwidth + 7) // 8, "big")


if __name__ == "__main__":
    runtime_CLI.parse_pvs_value = parse_pvs_value
    sswitch_CLI.main()
```

使用能导入 `runtime_CLI` 和 `sswitch_CLI` 的 Python 3 环境启动它，解释器与依赖的检查方法见 [1.3.3 节](./01-环境搭建.md#133-python-解释器与依赖)。端口应与交换机的 Thrift 配置一致：

```bash
python3 pvs-cli.py --thrift-port 9090
```

已修复该整数除法问题的 CLI 可直接使用 `simple_switch_CLI --thrift-port 9090`。在交换机已加载 JSON、绑定输入端口及端口 2 后，在 CLI 中输入：

```text
pvs_add MyParser.allowed_etypes 0x0800
pvs_add MyParser.allowed_etypes 0x88b5
pvs_get MyParser.allowed_etypes
```

此时 Ethernet 固定报头完整、EtherType 为 `0x0800` 或 `0x88b5` 的输入可以通过，其他 EtherType 及截断的 Ethernet 报头被丢弃。放行条件仅为 EtherType 匹配，所以 `0x0800` 后没有 IPv4 报头时也会通过。负载、填充和上层协议字段均按输入原样保留。

移除一个成员或清空集合：

```text
pvs_remove MyParser.allowed_etypes 0x0800
pvs_clear MyParser.allowed_etypes
```

| 当前集合内容       | 预期行为                                            |
| ------------------ | --------------------------------------------------- |
| 空集合             | 所有输入都不被放行                                  |
| `0x0800`、`0x88b5` | 仅放行 Ethernet 固定报头完整且 EtherType 匹配的输入 |
| 移除 `0x0800` 后   | 仅 `0x88b5` 被放行                                  |
| 清空后             | 再次不放行任何输入                                  |

这些命令直接修改运行时集合，名称以实际 JSON 为准，成员变更后即可重新测试放行结果。

## 13.8 `#include` 与代码组织

`#include` 在预处理时将文件内容插入当前位置，展开后的所有声明共同参与后续编译，并遵守所在位置的语法与可见性规则。

例如，可将 13.7 节程序按定义拆为：

```text
project/
├── main.p4       # include 与 main 实例
├── headers.p4    # ethernet_t、headers、metadata
├── parser.p4     # MyParser
└── controls.p4   # 其余五个 Control
```

对应的 `main.p4`：

```p4
#include <core.p4>
#include <v1model.p4>
#include "headers.p4"
#include "parser.p4"
#include "controls.p4"

V1Switch(MyParser(), MyVerifyChecksum(), MyIngress(), MyEgress(),
         MyComputeChecksum(), MyDeparser()) main;
```

先包含类型定义，再包含使用它们的处理块。公共文件可用 `#ifndef`／`#define`／`#endif` 保护，避免重复展开声明，查找其他目录的头文件时使用编译器的 `-I` 选项。表属于 Control 的局部声明，包含表定义的文件应在对应 Control 的声明区引入。
