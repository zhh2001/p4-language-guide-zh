# 14 · BMv2 编译与运行

本章使用仓库的 [L2 静态转发程序](../examples/02-l2-switch/l2_switch.p4)，说明编译、接口绑定、控制平面配置和报文验证。程序采用 P4₁₆ 与 V1Model，编译器和运行目标均按这一架构选择。

命令以仓库根目录为工作目录。验证环境为 p4c `1.2.5.10`（`8b6de3c57`）、BMv2 `1.15.0-2bdd0b7b`、Linux / Python 3.12。不同安装版本的可用参数以各工具的 `--help` 为准，基础环境检查见 [第 1 章](./01-环境搭建.md#14-环境自检)。

## 14.1 工具链与编译产物

```text
l2_switch.p4 ── p4c-bm2-ss ──┬── l2_switch.json
                            │       └── BMv2 的目标配置
                            └── l2_switch.p4info.txtpb
                                    └── 控制平面对象的名称、ID、键和动作参数

Linux 主机 ── veth ── simple_switch 或 simple_switch_grpc ── veth ── Linux 主机
                         ▲                   ▲
                    Thrift CLI          P4Runtime 客户端
```

| 组件                 | 本章用途                                           |
| -------------------- | -------------------------------------------------- |
| `p4test`             | 检查语言与类型规则，不生成 BMv2 可执行配置         |
| `p4c-bm2-ss`         | 将 V1Model 程序编译为 BMv2 JSON，并按需生成 P4Info |
| `simple_switch`      | 运行数据平面，提供 BMv2 专用 Thrift 控制接口       |
| `simple_switch_grpc` | 运行数据平面，提供 P4Runtime 服务                  |
| `simple_switch_CLI`  | 通过 Thrift 查看对象和配置表项                     |
| Mininet              | 建立主机、命名空间与虚拟链路，组织实验             |

P4Info 不是流水线实现，不能替代 BMv2 JSON；使用 Thrift CLI 时则不要求生成 P4Info。`simple_switch_grpc` 是否同时提供 Thrift 接口取决于构建配置，不能仅凭程序名判断。两种进程的接口区别见 [BMv2 目标说明](https://github.com/p4lang/behavioral-model/blob/main/docs/simple_switch.md#differences-between-simple_switch-and-simple_switch_grpc-processes)。

Mininet 不会自动解释 P4 程序，也不是 BMv2 的必要依赖。手工建立 network namespace 和 veth 同样可以运行实验。

## 14.2 编译

### 14.2.1 基本命令

```bash
mkdir -p build/ch14
p4test --std p4-16 examples/02-l2-switch/l2_switch.p4
p4c-bm2-ss --std p4-16 --target bmv2 --arch v1model \
    -o build/ch14/l2_switch.json \
    --p4runtime-files build/ch14/l2_switch.p4info.txtpb \
    examples/02-l2-switch/l2_switch.p4
```

| 参数                           | 说明                                     |
| ------------------------------ | ---------------------------------------- |
| `--std p4-16`                  | 指定语言版本                             |
| `--target bmv2 --arch v1model` | 选择目标与架构；不转换程序原有的架构接口 |
| `-o 文件.json`                 | BMv2 JSON 的输出路径                     |
| `--p4runtime-files 文件.txtpb` | 输出文本 protobuf 格式的 P4Info          |
| `-I 目录`                      | 增加预处理器的头文件搜索路径             |
| `-DNAME=VALUE`                 | 定义预处理宏                             |
| `--Werror`                     | 将警告视为错误；也可指定诊断类别         |

本机 p4c 支持 `.txtpb`、`.json` 和 `.bin` 等 P4Info 输出格式；旧的 `.txt` 后缀会产生弃用警告，配合 `--Werror` 可能导致构建失败。`l2_switch.p4info.json` 与 `l2_switch.json` 虽然都是 JSON，内容和用途仍然不同。

应从同一次成功编译取得 BMv2 JSON 与 P4Info，避免字段、动作或 ID 不一致。编译失败时不要继续运行上一次留下的产物。

### 14.2.2 编译失败的定位

| 现象                             | 检查方法                                                                                       |
| -------------------------------- | ---------------------------------------------------------------------------------------------- |
| 找不到 `core.p4` 或 `v1model.p4` | 核对安装前缀和实际头文件目录，必要时使用 `-I`；本机常见路径为 `/usr/local/share/p4c/p4include` |
| 类型或位宽不匹配                 | 查看诊断定位的实参与形参；显式转换也须符合类型规则，并考虑截断                                 |
| `V1Switch` 参数类型不匹配        | 对照架构声明检查六个处理块的顺序、类型和参数方向                                               |
| 语言检查通过，BMv2 后端失败      | 检查该目标对操作、Extern 和资源的支持；语言合法不代表后端可实现                                |
| 使用保留字后出现语法错误         | 检查声明名称与关键字，并从第一条语法错误开始修复                                               |

本机编译器识别 `P4C_16_INCLUDE_PATH`，可用它配置 P4₁₆ 的头文件搜索路径；设置前应先确认文件已经安装。另一个可直接观察的诊断是本例未使用的 `TYPE_IPV4` 常量：默认编译会报告 `unused` 警告，启用 `--Werror` 后则作为错误处理。

### 14.2.3 用 Makefile 固定编译命令

下面是可保存到仓库根目录的简化 Makefile，不是仓库已有文件。它每次重新编译，避免遗漏头文件变化；配方行开头须为 Tab：

```makefile
P4C ?= p4c-bm2-ss
SRC := examples/02-l2-switch/l2_switch.p4
OUT := build/ch14

.PHONY: build clean
build:
	mkdir -p $(OUT)
	$(P4C) --std p4-16 --target bmv2 --arch v1model \
	    -o $(OUT)/l2_switch.json \
	    --p4runtime-files $(OUT)/l2_switch.p4info.txtpb $(SRC)

clean:
	$(RM) $(OUT)/l2_switch.json $(OUT)/l2_switch.p4info.txtpb
```

## 14.3 启动 BMv2

以下两种启动方式择一使用。先按 14.4.1 节创建接口；两者都绑定相同接口，不应同时运行。14.4.2 节的 Mininet 脚本会自行创建接口并启动交换机，无须先执行本节命令。

### 14.3.1 `simple_switch`

```bash
sudo simple_switch --device-id 14 --thrift-port 9090 \
    --log-console --log-level debug \
    -i 1@p14s1 -i 2@p14s2 \
    build/ch14/l2_switch.json
```

`-i 1@p14s1` 将现有 Linux 接口 `p14s1` 绑定到 BMv2 端口 1，不会创建接口。端口编号必须与动作参数中的出端口一致；Thrift TCP 端口 9090 与这些数据平面端口没有对应关系。

命令在前台运行，另开终端配置表项和发包；实验结束后用 Ctrl+C 停止。`--device-id` 标识交换机实例，不是进程号或监听端口。多实例实验需分别安排设备 ID、监听端口和 IPC 地址。

### 14.3.2 `simple_switch_grpc`

```bash
sudo simple_switch_grpc --device-id 14 --thrift-port 9090 \
    --log-console --log-level debug \
    -i 1@p14s1 -i 2@p14s2 --no-p4 \
    -- --grpc-server-addr 127.0.0.1:50051
```

`--` 前是 BMv2 通用参数，后面是目标专用参数。这里显式选择 gRPC 地址，不能把 50051 当作所有版本的默认端口。

`--no-p4` 允许进程在没有流水线配置时启动。客户端随后完成主控仲裁，安装匹配的 P4Info 与 BMv2 JSON，再写入运行时表项；启动进程本身并未完成这些步骤。14.5.3 节给出本章的客户端操作。

普通接口收发不要求配置 CPU 端口。若要使用 P4Runtime 的 PacketIn／PacketOut，还须配置该目标的 `--cpu-port` 并让 P4 程序正确处理相应报文路径，不能仅靠启动 gRPC 服务获得此功能。

### 14.3.3 文本日志

调试时可使用 `--log-console --log-level debug`，需要更细信息时再改成 `trace`。本机支持 `trace`、`debug`、`info`、`warn`、`error`、`off`。

若要写文件，将 `--log-console` 换成 `--log-file build/ch14/switch.log --log-flush`。本机 `--log-console` 与 `--log-file` 互斥；`--log-flush` 仅对文件日志有意义。实际日志文件名及轮转后缀取决于日志实现，也可直接重定向控制台输出。

### 14.3.4 Nanomsg 日志与通知

这两个通道需要区分：

| 参数                                                     | 用途                                         |
| -------------------------------------------------------- | -------------------------------------------- |
| `--nanolog ipc:///tmp/ch14-events.ipc`                   | 发布解析、表命中／未命中、动作执行等事件日志 |
| `--notifications-addr ipc:///tmp/ch14-notifications.ipc` | 学习消息、表项老化等运行时通知               |

它们使用各自指定的 Nanomsg 地址，不是在 Thrift 的 9090 端口上发送同一种消息。启用事件日志时，将 `--nanolog` 加入交换机启动命令，再在另一终端订阅：

```bash
bm_nanomsg_events --socket ipc:///tmp/ch14-events.ipc \
    --json build/ch14/l2_switch.json
```

该功能需要 BMv2 构建时启用事件日志，客户端也要能导入 `nnpy` 等依赖。订阅开始后再发测试报文；它不是历史日志查询工具。

## 14.4 创建实验网络

本章只验证已知目的 MAC 的双向单播。两台主机位于同一 IPv4 子网，并设置静态邻居项，因此无需先配置 ARP 广播或路由器网关。L2 程序中的未知目的地址处理依赖多播组，本章不把它当作已经配置好的功能。

### 14.4.1 手工创建 namespace 与 veth

以下名称专用于本次实验，执行前确认没有同名资源。主机侧接口放入独立 network namespace，交换机侧接口留在根命名空间：

```bash
for n in 1 2; do
    sudo ip netns add p14h$n
    sudo ip link add p14s$n type veth peer name p14h$n
    sudo ip link set p14h$n netns p14h$n
    sudo ip -n p14h$n link set p14h$n name eth0
    sudo ip -n p14h$n link set eth0 address 02:00:00:00:00:0$n
    sudo ip -n p14h$n addr add 10.14.0.$n/24 dev eth0
    sudo ip -n p14h$n link set lo up
    sudo ip -n p14h$n link set eth0 up
    sudo ip link set p14s$n up
done
sudo ip -n p14h1 neigh replace 10.14.0.2 lladdr 02:00:00:00:00:02 nud permanent dev eth0
sudo ip -n p14h2 neigh replace 10.14.0.1 lladdr 02:00:00:00:00:01 nud permanent dev eth0
```

随后按 14.3.1 或 14.3.2 节启动交换机，并完成相应表项配置，最后测试：

```bash
sudo ip netns exec p14h1 ping -c 2 -W 1 10.14.0.2
sudo ip netns exec p14h2 ping -c 2 -W 1 10.14.0.1
```

停止交换机和抓包进程后，删除本次创建的命名空间与接口：

```bash
for n in 1 2; do
    sudo ip netns del p14h$n
    sudo ip link del p14s$n 2>/dev/null || true
done
```

删除 namespace 时，对端 veth 可能已随之删除，第二条命令允许这种情况。若创建过程在中途失败，只清理已经创建的本次资源。

校验和卸载、GRO／GSO 等设置会影响抓包和部分流量实验。先用 `ethtool -k 接口名` 查看；确需禁用时，在相关主机及交换机接口上设置并检查结果。不能把所有“不收包”都归因为未关闭卸载。

### 14.4.2 用 Mininet 管理同一拓扑

仓库编号示例的 `run.sh` 使用 namespace 和 veth，并没有 `topology/topology.py`。下面提供一个独立的 Mininet 版本；保存为 `build/ch14/mininet-l2.py`，先完成 14.2.1 节编译。

这里用无 IP 的根命名空间节点 `s1` 承载交换机侧接口，实际转发由单独启动的 BMv2 进程完成。Mininet 负责创建与清理节点和链路，不安装 Linux 网桥，也不运行 OpenFlow 控制器。API 说明见 [Mininet 文档](https://mininet.org/api/classmininet_1_1net_1_1Mininet.html)。

```python
from pathlib import Path
import socket
import subprocess
import time

from mininet.cli import CLI
from mininet.log import setLogLevel
from mininet.net import Mininet

setLogLevel("info")
work = Path("build/ch14").resolve()
with socket.socket() as probe:
    probe.bind(("127.0.0.1", 9090))  # 端口占用时，在创建拓扑前停止
net = Mininet(controller=None, build=False)
switch = None
try:
    h1 = net.addHost("h1", ip="10.14.0.1/24", mac="02:00:00:00:00:01")
    h2 = net.addHost("h2", ip="10.14.0.2/24", mac="02:00:00:00:00:02")
    s1 = net.addHost("s1", ip=None, inNamespace=False)
    net.addLink(h1, s1, port2=1)
    net.addLink(h2, s1, port2=2)
    net.start()
    h1.setARP(h2.IP(), h2.MAC())
    h2.setARP(h1.IP(), h1.MAC())

    with (work / "mininet-switch.log").open("w") as log:
        switch = subprocess.Popen([
            "simple_switch", "--device-id", "14", "--thrift-port", "9090",
            "--notifications-addr", "ipc://" + str(work / "notifications.ipc"),
            "--log-console", "--log-level", "debug",
            "-i", "1@s1-eth1", "-i", "2@s1-eth2",
            str(work / "l2_switch.json"),
        ], stdout=log, stderr=subprocess.STDOUT)

    deadline = time.monotonic() + 10
    while True:
        if switch.poll() is not None:
            raise RuntimeError("BMv2 启动失败，请查看 mininet-switch.log")
        try:
            with socket.create_connection(("127.0.0.1", 9090), timeout=0.2):
                break
        except OSError:
            if time.monotonic() >= deadline:
                raise RuntimeError("等待 Thrift 服务超时")
            time.sleep(0.1)

    result = subprocess.run([
        "simple_switch_CLI", "--thrift-port", "9090",
    ], input=(
        "table_add MyIngress.dmac MyIngress.forward 02:00:00:00:00:01 => 1\n"
        "table_add MyIngress.dmac MyIngress.forward 02:00:00:00:00:02 => 2\n"
        "table_dump MyIngress.dmac\n"
    ), text=True, capture_output=True, check=True)
    print(result.stdout, end="")
    if "Error" in result.stdout or result.stderr:
        raise RuntimeError("CLI 配置异常：" + result.stderr)
    if net.ping([h1, h2], timeout="2") != 0:
        raise RuntimeError("双向 ping 验证失败")
    print("PASS：Mininet + BMv2 双向单播验证完成")
    CLI(net)
finally:
    if switch is not None:
        switch.terminate()
        try:
            switch.wait(timeout=3)
        except subprocess.TimeoutExpired:
            switch.kill()
            switch.wait()
    net.stop()
```

确认当前 Python 能导入 Mininet，再把同一个解释器交给 `sudo`：

```bash
python3 -c 'import mininet; print(mininet.__file__)'
sudo "$(command -v python3)" build/ch14/mininet-l2.py
```

脚本使用 9090 端口及 `h1`、`h2`、`s1` 等名称，应在没有冲突的实验环境中运行。成功后可在 Mininet CLI 中执行 `h1 ping -c 2 h2`，输入 `exit` 退出。脚本停止自己启动的交换机，并由 `net.stop()` 清理拓扑；日志保存在 `build/ch14/mininet-switch.log`。

## 14.5 配置控制平面

### 14.5.1 `simple_switch_CLI`（Thrift）

手工启动 `simple_switch` 后，连接对应的 Thrift 服务：

```bash
simple_switch_CLI --thrift-port 9090
```

在一个尚未配置过的本章实例上输入：

```text
show_tables
show_actions
table_add MyIngress.dmac MyIngress.forward 02:00:00:00:00:01 => 1
table_add MyIngress.dmac MyIngress.forward 02:00:00:00:00:02 => 2
table_dump MyIngress.dmac
```

这两条表项与 14.4 节的主机 MAC、交换机端口一致。Mininet 脚本已经执行过它们，不应再重复添加。重复键可能报错，命令文件不是天然幂等的；修改已有条目时应使用相应更新或删除命令。

| 命令                        | 用途                                 |
| --------------------------- | ------------------------------------ |
| `table_add T A K => V`      | 为表 T 插入键 K 和动作 A 的参数 V    |
| `table_dump T`              | 查看表项、句柄和默认动作             |
| `table_modify T A handle V` | 修改指定句柄表项的动作及参数         |
| `table_delete T handle`     | 删除指定句柄的表项                   |
| `table_set_default T A V`   | 在允许修改默认动作的表上设置默认动作 |
| `counter_read C index`      | 读取实际存在的计数器 C               |
| `register_read R index`     | 读取实际存在的寄存器 R               |

本例未声明计数器或寄存器，不能套用 `counter_read pkt_count 0` 等命令。多播组及节点也要按所用 API 单独配置，P4 动作里写 `mcast_grp = 1` 不会自动建立组 1。

CLI 可能打印错误后继续接受下一条命令，进程退出码为 0 不能单独证明批量配置成功。应检查响应、读回表项，再发包验证。名称和动作参数顺序以编译产物为准。

### 14.5.2 P4Runtime

P4Runtime 使用 P4Info 描述对象，以数值 ID 编码控制请求，并通过 gRPC 与目标通信。本章只演示一个客户端安装流水线和写入直接表项的流程，仲裁、更新类型和错误处理见 [第 15 章](./15-P4Runtime控制平面.md)。

不要让 Thrift 和 P4Runtime 客户端同时修改本章同一张表，以免绕过某一接口维护的状态。两条实验路线分别使用新启动的交换机实例。

### 14.5.3 P4Runtime Shell

使用 [P4Runtime Shell](https://github.com/p4lang/p4runtime-shell) 时，Python 模块名是 `p4runtime_sh`，安装包名才是 `p4runtime-shell`。在已准备好依赖的 Python 环境中运行：

```bash
python3 -m p4runtime_sh --grpc-addr 127.0.0.1:50051 \
    --device-id 14 --election-id 0,1 \
    --config build/ch14/l2_switch.p4info.txtpb,build/ch14/l2_switch.json
```

这与 14.3.2 节的设备 ID、地址和流水线文件对应。`--config` 会提交流水线配置，不能把它当作无副作用的连接参数；重新提交配置可能清空运行时表项。已经装好正确流水线时可省略它。

本机旧版生成的 protobuf 模块与运行库存在兼容问题，直接启动会报 descriptor 错误；按 [1.3.3 节](./01-环境搭建.md#133-python-解释器与依赖)检查依赖。此环境的临时兼容方式是在上述命令前加 `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python`，该设置须在导入模块前生效。

进入 Shell 后，输入以下 Python 语句：

```python
to_h1 = table_entry["MyIngress.dmac"](action="MyIngress.forward")
to_h1.match["hdr.ethernet.dst"] = "02:00:00:00:00:01"
to_h1.action["port"] = "1"
to_h1.insert()

to_h2 = table_entry["MyIngress.dmac"](action="MyIngress.forward")
to_h2.match["hdr.ethernet.dst"] = "02:00:00:00:00:02"
to_h2.action["port"] = "2"
to_h2.insert()

table_entry["MyIngress.dmac"].read(lambda entry: print(entry))
```

本例的匹配键和动作参数都按 Shell 接受的字符串形式赋值。LPM 键也使用类似 `"10.0.1.0/24"` 的字符串，不能把 Python 元组直接当作该接口的 LPM 值。表项读回后，再按 14.4.1 节发 ping；无需重新编译。

## 14.6 抓包与日志定位

### 14.6.1 tcpdump

在手工拓扑的主机命名空间内抓包，先启动抓包，再发 ping：

```bash
sudo ip netns exec p14h2 tcpdump -ni eth0 -e -vv icmp
```

也可在交换机侧保存 PCAP：

```bash
sudo tcpdump -ni p14s2 -w build/ch14/port2.pcap
```

Mininet 脚本对应的接口名是 `s1-eth2`。比较双端抓包时，应区分接收方向与本机发包记录；只看到源主机发出了帧，不能证明交换机已经转发。

### 14.6.2 Wireshark

可用 Wireshark 打开保存的 PCAP，检查 Ethernet、ARP、IPv4、ICMP 等已知协议。解析 P4 自定义报头时，需要按线路格式编写或安装相应 dissector，例如 Lua 解析脚本。

若抓包显示校验和异常，先判断它是在发送端卸载前捕获，还是接收端确实收到了错误字节。IPv4 报头校验和、ICMP 校验和和 TCP／UDP 校验和覆盖的内容不同，不能统一归因于缺少某一次 `update_checksum`。

### 14.6.3 BMv2 日志

本章 L2 程序中，重点查找解析 Ethernet、应用 `MyIngress.dmac`、命中表项、执行 `MyIngress.forward` 和发送端口等记录。字段命名、日志文本与详细程度随版本和编译结果变化，不应把示意日志当作固定输出。

定位时沿一帧报文逐段检查：是否进入正确端口，解析是否成功，表键是什么，执行了哪个动作，最终发往哪个端口。需要关联抓包与日志时，可给测试流量添加可辨认的负载，或使用 `--dump-packet-data 字节数` 配合允许 `info` 消息的日志等级。

BMv2 还支持 `--use-files 秒数`：将 `-i 1@p1` 对应到 `p1_in.pcap` 与 `p1_out.pcap`，延迟指定秒数后回放输入。它适合检查输出字节和丢包分支；读完文件不等于交换机进程自动退出，也不能用这种回放替代真实接口验证。

## 14.7 组织可重复实验

一个运行脚本应明确输入源码、编译产物、端口映射、表项配置和通过标准。编译失败立即停止；启动失败保留诊断；退出时回收自己创建的进程、接口与命名空间。

仓库 [Hello P4 的运行脚本](../examples/01-hello/run.sh)提供了带清理逻辑的参考：

```bash
sudo bash examples/01-hello/run.sh
```

它验证从原入端口反射的行为，不是两主机互通测试。要验证本章的 L2 单播，可运行 14.4.2 节脚本。仅用固定 `sleep 1`、忽略 ping 的失败状态，或看到进程存在就报告成功，都不足以确认实验结果。

## 14.8 性能结果的适用范围

BMv2 主要用于开发、测试和调试。吞吐与时延取决于 P4 程序复杂度、构建选项、日志、报文长度、表项与流量分布、CPU 和虚拟化环境。测量结果应与这些条件一同报告，其适用范围是被测配置，不能直接外推到 ASIC 或其他软件目标。详见 [BMv2 性能说明](https://github.com/p4lang/behavioral-model/blob/main/docs/performance.md)。

`simple_switch` 有多个处理线程，也不存在本章所用版本的通用 `--dpdk` 启动开关。DPDK 后端属于另一条编译与运行路线，须核对其架构及运行时支持。性能报告至少应给出程序版本、软硬件环境、包长、流量模型、日志设置，以及吞吐、丢包和时延的测量方法。

## 14.9 常见问题

| 现象                                 | 优先检查                                                           |
| ------------------------------------ | ------------------------------------------------------------------ |
| 编译成功但交换机无法启动             | JSON 是否来自成功构建、接口是否存在、权限及监听端口是否冲突        |
| 有输入抓包，交换机日志却没有收包记录 | 绑定的是 veth 哪一端、接口是否启用、进程是否存活、日志等级是否足够 |
| CLI 找不到表或动作                   | 是否连接了正确实例，用 `show_tables`、`show_actions` 对照当前 JSON |
| 表项写入后 ping 仍不通               | 两个方向的表项、主机 MAC/IP、静态邻居项或 ARP 路径是否完整         |
| P4Runtime 连接被拒绝                 | gRPC 进程、绑定地址和端口；这通常还没进入设备 ID 或仲裁检查        |
| gRPC 可连接但写请求失败              | 设备 ID、主控身份、已安装的 P4Info、对象 ID、键和动作参数          |
| 有 ingress 记录但没有预期输出        | 解析错误、动作分支、最终出端口、多播组、egress 丢弃和队列状态      |
| 抓包显示校验和错误                   | 捕获位置与卸载状态，以及实际修改了哪些受校验和覆盖的字段           |

Ingress 的默认丢弃端口通常是 511，但可以通过目标参数改变；Egress 丢弃、多播未配置和不存在的出接口也可能导致收不到报文。不要仅搜索一条固定的 `egress_spec=511` 日志来排除其他原因。

## 14.10 本章小结

先确认程序与架构匹配，再生成一致的编译产物、建立接口、启动目标并配置控制平面。实验通过的依据应包括表项读回和报文结果，分别判断编译、管理连接与数据平面是否正常。
