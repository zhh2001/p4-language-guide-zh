# 03 · 第一个 P4 程序：Hello P4

本章在 BMv2 `simple_switch` 上运行一个报文反射程序：从端口 1 收到的报文仍从端口 1 发出，端口 2 同理。通过这个例子，可以观察 V1Model 要求的程序结构，并区分编译成功、进程启动和报文处理正确这三个结果。

本例不实现两台主机之间的转发，也不生成 ICMP Echo Reply。验证依据是接收方向上实际出现的反射帧，而不是 ping 是否成功。

## 3.1 实验拓扑

```mermaid
flowchart LR
    H1["h1：10.0.0.1/24"] <-->|"veth · 端口 1"| S["s1：BMv2 / Hello P4"]
    S <-->|"端口 2 · veth"| H2["h2：10.0.0.2/24"]
```

`run.sh` 用 Linux network namespace 分别隔离两台主机，并通过两对 veth 连接到 BMv2。它没有调用 Mininet，也不提供 Mininet CLI。

图中的 `h1`、`h2` 是逻辑名称。脚本为命名空间和交换机侧接口生成本次运行专用的名字，主机内的接口均为 `eth0`，以避免与已有实验重名。

## 3.2 程序结构

完整源码见 [hello.p4](../examples/01-hello/hello.p4)。下面各段按顺序拼接，可组成完整程序。这里的六个可编程块及其参数来自 [V1Model 架构声明](https://github.com/p4lang/p4c/blob/main/p4include/v1model.p4)，不是所有 P4 架构都采用同样的接口。

### 3.2.1 引入声明并定义类型

```p4
#include <core.p4>
#include <v1model.p4>

struct headers  { }
struct metadata { }
```

`core.p4` 声明 `packet_in`、`packet_out` 等核心接口；`v1model.p4` 声明 `standard_metadata_t` 和 `V1Switch` 等架构接口。本例显式包含两者，使依赖关系清楚。

`headers` 与 `metadata` 都是用户定义的类型。本例不提取报头，也不使用自定义元数据，因此使用空结构体，仍按架构要求传递它们。

### 3.2.2 Parser

```p4
parser MyParser(packet_in packet,
                out headers hdr,
                inout metadata meta,
                inout standard_metadata_t std_meta) {
    state start {
        transition accept;
    }
}
```

解析器从 `start` 开始，立即到达 `accept`，没有提取或跳过任何报文字节。`accept` 表示解析成功结束，后续仍会执行 Ingress 等处理步骤；出端口尚未由这段代码决定。

### 3.2.3 VerifyChecksum

```p4
control MyVerifyChecksum(inout headers hdr, inout metadata meta) {
    apply { }
}
```

V1Model 要求提供这个控制块，本例将其留空。因此程序没有验证 IPv4 等协议的校验和，不能据此判断输入报文在协议层面是否合法。

### 3.2.4 Ingress

```p4
control MyIngress(inout headers hdr,
                  inout metadata meta,
                  inout standard_metadata_t std_meta) {
    apply {
        std_meta.egress_spec = std_meta.ingress_port;
    }
}
```

本例的出端口选择由这一条赋值完成。BMv2 在收到报文时设置 `ingress_port`；程序把它赋给 `egress_spec`，选择同一个端口作为单播出端口。字段含义见 [BMv2 的标准元数据说明](https://github.com/p4lang/behavioral-model/blob/main/docs/simple_switch.md#standard-metadata)。

例如，启动参数 `-i 1@某接口` 将该接口绑定为 BMv2 端口 1。从它进入的普通报文，其 `ingress_port` 为 1，执行本例后 `egress_spec` 也为 1。端口号来自 BMv2 的接口绑定，不是 Linux 的接口索引。

这里的 `std_meta` 是参数名，`standard_metadata_t` 是参数类型。本程序中各块使用同一命名约定，便于阅读。

### 3.2.5 Egress 与 ComputeChecksum

```p4
control MyEgress(inout headers hdr,
                 inout metadata meta,
                 inout standard_metadata_t std_meta) {
    apply { }
}

control MyComputeChecksum(inout headers hdr, inout metadata meta) {
    apply { }
}
```

本例没有出方向修改，也不需要重新计算协议校验和，因此这两个控制块留空。

### 3.2.6 Deparser

```p4
control MyDeparser(packet_out packet, in headers hdr) {
    apply { }
}
```

BMv2 保留解析后尚未消费的字节，反解析时将需要输出的有效报头放在这些字节前面。本例的 Parser 没有消费字节，Deparser 也没有添加报头，原来的报文字节便得以保留。对应实现可查阅 [BMv2 Deparser 源码](https://github.com/p4lang/behavioral-model/blob/main/src/bm_sim/deparser.cpp)。

这个结论依赖本例的解析方式和目标行为。如果以后提取了以太网报头，要在输出时保留它，就需要相应的 `emit`；不能照搬空 Deparser。

### 3.2.7 实例化顶层包

```p4
V1Switch(
    MyParser(),
    MyVerifyChecksum(),
    MyIngress(),
    MyEgress(),
    MyComputeChecksum(),
    MyDeparser()
) main;
```

这段声明创建名为 `main` 的顶层包实例，并按 `V1Switch` 的接口顺序传入六个块。块的参数类型、方向和顺序必须与架构声明兼容。

## 3.3 编译

以下命令均从**仓库根目录**执行。基础工具链参照 [第 1 章](./01-环境搭建.md)；本章的两主机验证脚本还要求 Linux 上的 Python 3.12 或更高版本，因为它使用标准库的 [`os.setns`](https://docs.python.org/3.12/library/os.html#os.setns)在主机命名空间中创建抓包套接字。脚本不依赖 Scapy。

```bash
bash examples/01-hello/build.sh
```

默认在 `examples/01-hello/` 下生成：

| 文件                 | 用途                                                  |
| -------------------- | ----------------------------------------------------- |
| `hello.json`         | BMv2 加载的目标程序配置                               |
| `hello.p4info.txtpb` | 文本格式 P4Info，描述控制平面接口；本例运行时不使用它 |

本例没有表，不需要下发表项。生成 P4Info 只是展示编译产物，不表示已经启动 P4Runtime 服务。

编译脚本也接受一个可选的输出目录参数，例如：

```bash
bash examples/01-hello/build.sh /tmp/hello-build
```

运行脚本会另行把当前源码编译到独立临时目录，不复用上述产物，避免修改源码后误加载旧 JSON。

## 3.4 自动验证报文反射

```bash
sudo bash examples/01-hello/run.sh
```

脚本依次编译程序、创建两主机拓扑、启动 BMv2，再调用 [verify.py](../examples/01-hello/verify.py)验证数据平面。BMv2 通过 `-i` 参数绑定两个接口；自检不使用 Thrift 控制接口，监听端口由系统分配，避免固定占用 9090。

验证程序在两台主机的接口上先创建套接字，再依次发出测试帧。每台主机分别发送 60、128、1514 字节的以太帧，长度不含 FCS。测试帧使用广播目的 MAC、实验用 EtherType `0x88b5` 和随机标识，不依赖 ARP 解析。

每次发送都检查：

1. 原主机收到一份与发送内容逐字节一致的帧；本机发包记录不计入结果。
2. 另一主机在观察窗口内没有收到该测试帧。
3. 原主机在观察窗口内没有收到重复副本。

等待反射的超时为 3 秒；收到反射后继续观察 0.3 秒。这是功能检查，不是吞吐量、时延或长期丢包率测试。正常输出包含：

```text
PASS：h1，60 字节，反射帧一致；观察窗口内另一主机未收到测试帧
PASS：h1，128 字节，反射帧一致；观察窗口内另一主机未收到测试帧
PASS：h1，1514 字节，反射帧一致；观察窗口内另一主机未收到测试帧
PASS：h2，60 字节，反射帧一致；观察窗口内另一主机未收到测试帧
PASS：h2，128 字节，反射帧一致；观察窗口内另一主机未收到测试帧
PASS：h2，1514 字节，反射帧一致；观察窗口内另一主机未收到测试帧
PASS：两个端口的 Hello P4 反射验证完成
```

默认情况下，验证完成后脚本退出。失败时返回非零状态；正常结束、报错、SIGINT 或 SIGTERM 都会触发清理，删除本次创建的 BMv2 进程、接口、命名空间及临时目录。

## 3.5 保留拓扑并观察 ARP

需要手工检查时，在终端一运行：

```bash
sudo bash examples/01-hello/run.sh --keep
```

验证通过后脚本继续运行，并打印本次命名空间名称、抓包命令、ping 命令及日志位置。手工观察结束后，先停止其他终端中的抓包命令，再在终端一按 Ctrl+C 结束实验并清理资源。

在终端二先启动抓包。下面的 `hello-XXXXXX-h1` 必须替换为脚本实际输出的名称，也可以直接复制脚本打印的完整命令：

```bash
h1_ns=hello-XXXXXX-h1
sudo ip netns exec "$h1_ns" tcpdump -Q in -n -e -i eth0 arp
```

在终端三发送 ping，同样替换命名空间名称：

```bash
h1_ns=hello-XXXXXX-h1
sudo ip netns exec "$h1_ns" ping -c 2 -W 1 10.0.0.2
```

此时 h1 首先需要知道 `10.0.0.2` 的 MAC 地址，因此发出 ARP 请求。Hello P4 将请求从原端口反射回来，h2 收不到它，也就不会提供 ARP 应答。h1 无法完成邻居解析，通常还没有发出承载 ICMP 请求的以太帧，ping 就已失败。

终端二应能捕获接收方向的 ARP 请求。`-Q in` 排除了本机发送方向的抓包记录，所以看到的请求是返回的报文。默认抓包同时包含收发方向，仅看到自己发出的请求不能证明反射成功。

即使另行配置静态邻居表，使 ICMP 请求能够发出，本程序也只是反射原始帧，不会把 Echo Request 改成 Echo Reply。因此不能用 ping 成功作为本例的验收条件。

## 3.6 回顾一次处理过程

| 阶段                | 本例中的行为                                    |
| ------------------- | ----------------------------------------------- |
| 接收与 Parser       | BMv2 记录入端口；解析器直接结束，不消费报文字节 |
| VerifyChecksum      | 不执行协议校验和验证                            |
| Ingress             | 将 `ingress_port` 赋给 `egress_spec`            |
| BMv2 内部转发与排队 | 根据所选端口将报文送往出方向处理                |
| Egress              | 不修改报文                                      |
| ComputeChecksum     | 不更新协议校验和                                |
| Deparser 与发送     | 不添加报头，保留未解析的字节，并从原端口发出    |

这是 V1Model 在 BMv2 上的处理路径。`hdr`、`meta` 和 `std_meta` 各有用途，也不是每个块都接收三者；查看函数签名比笼统地说“数据都由标准元数据传递”更准确。

## 3.7 常见问题

| 现象                         | 检查方法                                                           |
| ---------------------------- | ------------------------------------------------------------------ |
| 找不到 `standard_metadata_t` | 检查是否包含 `v1model.p4`，以及编译器能否找到架构头文件            |
| 顶层包或块的类型检查失败     | 对照 `V1Switch` 检查六个块的签名、顺序和 `main` 实例               |
| 脚本提示缺少 `os.setns`      | 检查 `sudo` 环境中的 `python3` 版本；可能与当前虚拟环境不同        |
| BMv2 启动失败                | 查看脚本输出的日志；动态库错误可用 `ldd` 检查实际缺失的依赖        |
| 接收到报文但验证仍失败       | 检查是否改写了字节、发往另一端口或生成了重复副本                   |
| 只看到 ARP，没看到 ICMP      | 邻居解析尚未完成，参照 3.5 节分析                                  |
| 抓包命令找不到命名空间       | 默认运行已清理拓扑，或使用了上一次运行的名称；重新用 `--keep` 启动 |

## 3.8 本章验证范围

本章在第 1 章记录的 Ubuntu 24.04 / WSL2 环境中，使用 p4c `1.2.5.10`、BMv2 `1.15.0-2bdd0b7b` 和 Python `3.12.3` 验证。正文各段源码拼接后可编译；自动实验检查两个端口与三种帧长。

反例检查使用临时修改的程序：全部丢弃测试帧、把报文转发到另一端口、改写报文字节，均被验证程序判为失败。手工抓包确认了返回的 ARP 请求；编译失败、启动失败、SIGINT 与 SIGTERM 后的资源清理也已检查。这些结果针对本例的功能，不代表其他章节的协议处理逻辑已经通过测试。
