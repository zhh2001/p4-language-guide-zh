# 示例 05 · ECMP 等价多路径

本例先按目的 IPv4 前缀选择 ECMP 组，再对报文的哈希键计算 CRC32，选择组内下一跳。选中下一跳后改写源、目的 MAC，TTL 减 1，并更新 IPv4 报头校验和。

程序使用 V1Model，在 BMv2 上验证前缀选组、流到下一跳的映射和报头改写。`hash` 接口见[第 12 章](../../docs/12-外部对象Extern.md#127-hash)，转发流水线见[第 11 章](../../docs/11-V1Model架构.md)。

## 拓扑与实验范围

```text
                   端口 2 ── nh1（接收端）
                  /
h1 ── 端口 1 ── s1
                  \
                   端口 3 ── nh2（接收端）
```

| 节点 | IPv4 地址     | MAC 地址            | BMv2 端口 |
| ---- | ------------- | ------------------- | --------- |
| h1   | `10.0.1.1/24` | `00:00:00:00:00:01` | 1         |
| nh1  | `10.0.2.2/24` | `00:00:00:00:00:02` | 2         |
| nh2  | `10.0.2.3/24` | `00:00:00:00:00:03` | 3         |

每个节点是独立的 network namespace，主机侧接口名为 `eth0`，经 veth 连接 BMv2。脚本直接创建这些资源，不调用 Mininet。命名空间与交换机侧接口名称由脚本生成。

h1 的默认网关为 `10.0.1.254`，永久邻居项将其映射到 `00:00:00:01:00:00`，供主机封装发往网关的 IPv4 报文。交换机不回应 ARP 或网关 ping。nh1、nh2 模拟两个下一跳接收端，拓扑配置的是 h1 到这两个接口的单向转发。测试目的地址 `10.0.2.10` 未配置给任何主机，实验以在选定下一跳接口收到正确报文为成功标准。

自动验证使用原始以太帧，直接指定网关 MAC，绕过 Linux 的路由和邻居查询。上述 Linux 路由与永久邻居项供手工使用普通 IP 工具发包时选取下一跳。

## 两张表如何选路

| 表                           | 匹配键                    | 动作                                        |
| ---------------------------- | ------------------------- | ------------------------------------------- |
| `MyIngress.ipv4_lpm`         | 目的 IPv4，最长前缀匹配   | 设置组 ID、组大小并计算组内索引             |
| `MyIngress.ecmp_group_to_nh` | 组 ID、组内索引，精确匹配 | 写入下一跳 MAC、出端口 MAC 与端口，TTL 减 1 |

两张表的默认动作都固定为 `drop()`，也允许安装显式丢弃表项。第一张表执行 `drop` 后立即退出 Ingress，只有执行选组动作后才继续处理。组大小为 0 时也会直接丢弃，此检查由 Ingress 显式完成，因为 V1Model 的 `hash` 在 `max=0` 时返回 `base`，不会自行拒绝空组。

组大小 N 大于 0 时，设哈希键的 CRC32 值为 H，则组内索引为 `H % N`。本例 `base=0`，默认 N=2，索引为 0 或 1。第二张表须为该组配置所有可达索引，缺少某个索引时，对应报文执行默认丢弃动作。N 可以取非 2 的幂，组表的 1024 项容量由所有组的成员共同占用。

[runtime/s1-commands.txt](./runtime/s1-commands.txt)先安装两个下一跳，再安装引用它们的路由：

```text
table_add MyIngress.ecmp_group_to_nh MyIngress.set_nh 1 0 => 00:00:00:00:00:02 00:00:00:01:00:01 2
table_add MyIngress.ecmp_group_to_nh MyIngress.set_nh 1 1 => 00:00:00:00:00:03 00:00:00:01:00:02 3
table_add MyIngress.ipv4_lpm MyIngress.set_ecmp_group 10.0.2.0/24 => 1 2
```

配置者将两个下一跳视为等价路径，P4 程序按已有表项转发。若要根据路径代价或链路状态调整成员，需要控制平面检测并更新配置。

## 哈希能保证什么

哈希键按源 IPv4、目的 IPv4、协议号、源端口、目的端口的顺序拼接，共 104 位。本机 BMv2 按网络字节序构造这 13 字节输入。对于通过输入检查的报文，在哈希算法、组大小和索引映射都不变时，相同五元组选择同一下一跳。负载内容、TCP 序号、IPv4 identification 和 TTL 不参与哈希。

多个流可以映射到同一索引。各出口的负载取决于分配到的流数，以及每条流的报文数、字节数和速率。流数相等时，链路负载仍可能不同。本例使用 CRC32 分桶，具体样本的分布由验证程序统计。

本例为每个报文重新计算索引，改变 N 或索引到下一跳的映射可能迁移已有流。反向报文交换了源、目的地址和端口，会重新计算哈希。需要双向选择对称路径时，应另行设计哈希键或映射关系。

## 输入检查

Parser 只处理无 VLAN、IHL 为 5、未分片的 IPv4 报文，检查版本和 IPv4 总长度。总长度不得小于 20，也不得超过实际输入中 Ethernet 报头之后的字节数。解析错误、IPv4 报头校验和错误、TTL 为 0 或 1，以及非 IPv4 报文均丢弃。

TCP 至少包含 20 字节固定报头，`dataOffset` 至少为 5，声明的报头长度不得超过 IP 负载。UDP 至少包含 8 字节报头，`length` 不得小于 8 或超过 IP 负载。TCP 选项保留在未解析负载中，UDP 长度小于 IP 负载时也不裁去多余字节。

非 TCP/UDP 协议的两个端口键固定为 0，实际只按源地址、目的地址和协议号区分。IPv4 首片和后续片全部拒绝，判断条件是 MF 为 1 或分片偏移不为 0。此检查在读取 TCP/UDP 报头前完成，后续片的数据不会被当作端口读取。

TCP/UDP 校验和、TCP 选项内容和连接状态不参与检查。转发只修改 MAC、TTL 和 IPv4 报头校验和，传输层伪首部不变，因此保留传输层校验和原值。IPv4 总长度以外的帧尾字节也会随 BMv2 未解析负载保留。

## 编译与 Thrift 实验

依赖 `p4c-bm2-ss`、`simple_switch`、`simple_switch_CLI`、`ip`、`timeout`，以及支持 `os.setns` 的 Linux Python 3.12+，手工抓包还需 `tcpdump`。数据平面验证只使用 Python 标准库。安装与检查方法见[第 1 章](../../docs/01-环境搭建.md)。

从**仓库根目录**执行：

```bash
bash examples/05-ecmp/build.sh
sudo bash examples/05-ecmp/run.sh
```

`build.sh` 用于单独编译，默认在示例目录生成 `ecmp.json` 和 `ecmp.p4info.txtpb`，也可用第一个参数指定输出目录。`run.sh` 包含编译步骤，每次将当前源码编译到临时目录，创建拓扑，确认本进程的 Thrift 服务就绪，再加载配置并验证。

脚本为新实例加载一次配置，先过滤整行注释与空行，再检查 CLI 错误文本并读回两张表。手工加载时也需先过滤配置文件，本机 CLI 将 `#` 注释视为未知命令，空行会重复上一条命令。修改已有实例时应根据实际表项句柄操作。

Thrift 默认端口为 9090，已被占用时在创建拓扑前退出。可通过环境变量另选空闲端口：

```bash
sudo env P4_ECMP_THRIFT_PORT=9091 bash examples/05-ecmp/run.sh
```

## 自动验证

[verify.py](./verify.py)在三个命名空间中打开原始套接字，从 h1 发送带随机标识的报文，并检查实际输出。它排除本机发包记录，以及引用原始负载的 ICMP 错误报文，逐字节比较 MAC、TTL、IPv4 校验和与其余内容。

先执行 33 个用例：

| 检查内容                                      | 预期结果                          |
| --------------------------------------------- | --------------------------------- |
| 60、128、1514 字节 UDP 帧，TTL 2/255          | 正确改写 MAC、TTL 和 IPv4 校验和  |
| 改变源地址、目的地址、目的端口或协议          | 按相应哈希键选择下一跳            |
| ICMP 与其他 IP 协议                           | 两个端口键为 0，按参考 CRC32 选路 |
| TCP 选项、帧尾字节、错误 TCP 校验和           | 对应字节保持不变                  |
| TTL 0/1、无路由                               | 丢弃                              |
| 错误版本、IHL、IPv4/TCP/UDP 长度、IPv4 校验和 | 丢弃                              |
| IPv4 选项、首片、后续片、非 IPv4、VLAN        | 丢弃                              |

随后构造源端口为 10000~10499 的 500 条 TCP 流，每条发送两帧。两帧的五元组相同，TTL 分别为 64 和 63，TCP 序号、IPv4 identification 和负载标识分别随机生成。验证程序用 Python `zlib.crc32` 独立计算本机 BMv2 的预期落点，逐帧检查结果。组内索引依赖输入字段的拼接顺序和目标的算法实现，不能据此假定不同目标一定产生相同结果。

本机这组样本中，nh1、nh2 各接收 250 条流、500 帧，该分布对应上述固定的五元组集合。脚本限速分批发送，避免将软件队列的突发丢包混入功能验证。边界用例收到预期输出后继续观察 0.2 秒，丢弃用例同样观察 0.2 秒。批量用例最多等待 3 秒，全部收齐后再观察 0.05 秒，检查重复副本与错误出口。帧长不含 FCS。

配置失败、报文缺失、字节不符、重复输出或选错端口都会返回非零状态。全部通过后输出：

```text
PASS：ECMP 选路、同流稳定性、报头改写和丢弃验证完成
```

## P4Runtime 配置方式

[runtime/ctrl.py](./runtime/ctrl.py)提供另一条可运行的配置流程。需要 `simple_switch_grpc`，以及可导入 `grpc`、`p4.v1`、`p4.config.v1` 的 Python 环境。依赖说明与旧版 protobuf 生成模块的兼容设置见[第 15 章](../../docs/15-P4Runtime控制平面.md#154-python-客户端环境)。

若 `python3` 已具备这些依赖：

```bash
sudo bash examples/05-ecmp/run.sh --p4runtime
```

需要使用虚拟环境或本机的旧模块兼容设置时，可显式指定解释器。例如，本机使用：

```bash
sudo env P4_ECMP_PYTHON="$HOME/p4dev-python-venv/bin/python" \
  PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python \
  bash examples/05-ecmp/run.sh --p4runtime
```

此模式启动 `simple_switch_grpc --no-p4`，使用本次交换机进程对应的设备 ID。gRPC 绑定 `127.0.0.1:50051`，可通过 `P4_ECMP_GRPC_PORT` 更改。Thrift 端口仍由 `P4_ECMP_THRIFT_PORT` 指定，两个端口须不同且可用。系统 `python3` 负责网络验证，`P4_ECMP_PYTHON` 只负责控制客户端。

客户端从 P4Info 按名称查找表、动作、匹配字段和参数的 ID，按声明位宽检查数值，并使用大端最短非空字节串编码。它保持仲裁流开放，确认获得对应设备和 election ID 的主控身份后才安装流水线。

客户端使用 `VERIFY_AND_COMMIT` 为本例新建的专用实例安装流水线，此操作会清除原有转发状态。组内成员写入成功后，再以独立请求安装路由。写入请求采用默认的 `CONTINUE_ON_ERROR`，已成功的更新会保留，批量操作的语义见 [15.3 节](../../docs/15-P4Runtime控制平面.md#153-rpc-与批量操作)。

客户端遍历 `Read` 的全部响应，按字段 ID 和数值核对三条表项，再关闭仲裁流与连接并退出。退出后表项仍保留，`run.sh` 随后执行与 Thrift 模式相同的 1033 帧数据平面验证。独立调用客户端时，可通过 `--address`、`--device-id`、`--election-id`、`--p4info`、`--json` 指定参数，默认产物路径相对于示例目录，不依赖当前工作目录。

## 手工观察与清理

```bash
sudo bash examples/05-ecmp/run.sh --keep
# 也可组合使用 --p4runtime --keep
```

验证后保留拓扑，脚本打印实际命名空间、抓包命令和重新运行验证的命令。Thrift 模式还会打印 CLI 地址，可执行 `table_dump MyIngress.ipv4_lpm` 和 `table_dump MyIngress.ecmp_group_to_nh` 查看配置。

观察下一跳时，在 nh1、nh2 的 `eth0` 上用 `tcpdump -Q in` 抓取入方向报文，再按测试五元组和负载标识统计。自动验证中 500 条 TCP 流可用过滤条件 `tcp and dst host 10.0.2.10 and src portrange 10000-10499` 筛选。同一源端口对应的两帧应落在同一接收端，输出 TTL 分别为 63 和 62。与 h1 发出的原始帧比较时，MAC、TTL 和 IPv4 校验和按选中下一跳改写，IP 地址与 TCP 内容保持不变。Linux 接口 RX 总数还包含其他背景报文，应以筛选后的测试报文核对分流结果。

正常退出、报错、SIGINT 或 SIGTERM 时，脚本只停止自己启动的交换机，并删除本次创建的接口、命名空间和临时目录。`--keep` 模式下按 Ctrl+C 结束，手工启动的抓包程序应先停止。需要保留日志时，请在退出前复制脚本打印的临时目录。

## 练习

- 增加更具体的前缀，检查最长前缀匹配。再分别配置空组、缺失索引和显式丢弃表项，确认不会继续转发。
- 扩为四个不同下一跳时，修改 N 和组表，创建并接通新增端口与接收端，更新 MAC、路由及验证预期。用抓包确认报文到达四个独立接收端。
- 比较 `action_selector` 的选组接口与手写哈希表，查看编译产物及目标上的资源映射，分析两种实现的配置方式和处理开销。
- 研究成员增删时的流迁移，比较模运算、固定桶间接映射和一致性哈希，统计配置变化前后的流落点。若另行保存流状态，还需设计冲突处理、超时和故障后的迁移规则。

实测环境：Ubuntu 24.04 / WSL2，p4c `1.2.5.10`、BMv2 `1.15.0-2bdd0b7b`、Python `3.12.3`。
