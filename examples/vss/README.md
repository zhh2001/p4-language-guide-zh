# VSS · Very Simple Switch 架构参考

本目录依据 P4<sub>16</sub> 语言规范 **1.2.5 第 5 节**整理，用于阅读架构接口与完整程序的装配方式。VSS 是规范中的教学架构，第 5.1 节给出 P4 接口，第 5.2 节说明固定功能模块的行为，第 5.3 节给出 IPv4 转发程序。规范版本入口见[附录 C](../../appendix/C-学习资源.md#c1-官方规范与参考)。

本地版本保留规范示例的四张表和处理顺序，统一动作列表语法，增加头文件包含保护、临时下一跳初始化和显式的路由丢弃分支。代码不是规范原文的逐字副本。架构与 Package 的基础知识见[第 10 章](../../docs/10-架构与包.md)。

## 文件与架构边界

| 文件                                                         | 内容                                                                                |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| [very_simple_switch_model.p4](./very_simple_switch_model.p4) | 端口类型、输入输出元数据、Parser／Control 接口、`VSS` 包和 `Checksum16` extern 声明 |
| [vss.p4](./vss.p4)                                           | Ethernet／IPv4 报头、解析器、四张匹配动作表、Deparser 与 `main` 实例                |

两个文件描述了接口和可编程逻辑。端口收发、输入仲裁、Parser 错误传递、输出分发、负载拼接与校验和 extern 的实际实现，需要由支持 VSS 的目标提供。仅声明 `package VSS` 或 `extern Checksum16` 不会自动产生这些实现。

本仓库的可运行编号示例使用 V1Model 与 BMv2 `simple_switch`。本地安装的 BMv2 后端不接受这里的 `VSS` 顶层包，因此本目录提供语言层检查，不提供拓扑脚本或转发实测。需要运行 IPv4 转发实验时，可使用[示例 03](../03-ipv4-router/README.md)。

## 接口与端口

```text
TopParser → TopPipe → TopDeparser
               │
               └─ outCtrl.outputPort → VSS 固定功能输出分发
```

`TopParser` 输出 `Parsed_packet`。架构将这些报头、解析错误和 `InControl` 交给 `TopPipe`，后者修改报头并填写 `OutControl`。`TopDeparser` 发出修改后的报头，剩余负载由架构按其规定拼接。`VSS(TopParser(), TopPipe(), TopDeparser()) main` 绑定三个实现，其参数类型和方向须符合架构声明。

`PortId` 为 `bit<4>`，规范为 VSS 定义了以下端口用途：

| 数值        | 用途               |
| ----------- | ------------------ |
| 0～7        | 物理 Ethernet 端口 |
| 13（`0xD`） | 重循环输入／输出   |
| 14（`0xE`） | CPU 输入／输出     |
| 15（`0xF`） | 丢弃输出           |

4 位能表示 16 个数值，不表示设备有 16 个物理端口。8～12 属于无效输出端口，规范要求将对应报文丢弃。这些编号属于 VSS 的约定，不能直接用作 V1Model 的端口配置。

CPU 路径还有一项容易忽略的规定：VSS 将**原始输入报文**送给控制平面，丢弃 Deparser 生成的那份报文。因此，不能因为 `TopPipe` 已将 TTL 减 1，就推断 CPU 收到的报文也带着修改后的 TTL。该行为由 VSS 固定功能模块规定，P4 文件中的赋值本身不足以说明它。

## 解析与校验和

Parser 先提取 Ethernet 报头，仅在 EtherType 为 `0x0800` 时继续解析 IPv4。`select` 没有默认分支，其余 EtherType 会进入 `reject`，并产生 `error.NoMatch`。IPv4 解析检查版本为 4、IHL 为 5，再验证报头校验和。提取所需字节不足时会产生 `PacketTooShort`。这些错误由架构传入 `parseError`，`TopPipe` 随后设置丢弃端口并返回。

`Checksum16` 是 VSS 的架构专用对象，不属于 `core.p4`。两个 `ck` 分别在 Parser 与 Deparser 中实例化，方法职责如下：

| 方法           | 用途                                         |
| -------------- | -------------------------------------------- |
| `clear()`      | 开始一次新的计算                             |
| `update(data)` | 按字段声明顺序加入待计算的数据               |
| `remove(data)` | 从当前校验和状态中移除数据贡献，本例没有调用 |
| `get()`        | 取得 16 位反码校验和                         |

验证输入时，`ck.update(p.ip)` 包含报文原有的 `hdrChecksum` 字段。按 VSS 定义的反码校验和语义，有效 IPv4 报头的 `ck.get()` 应为 0。这不表示报文中携带的校验和字段本身应为 0。

生成输出时，程序先把 `hdrChecksum` 置 0，再将整个 IPv4 报头加入计算，最后写回结果。这里清零是因为计算对象包含校验和字段。V1Model 常见写法则从计算元组中排除该字段，两种 API 的数据范围不同，不能机械套用同一段代码。

## 四张表与配置前提

| 执行顺序 | 表           | 匹配键              | 主要动作                     |
| -------- | ------------ | ------------------- | ---------------------------- |
| 1        | `ipv4_match` | 目的 IPv4，LPM      | 设置下一跳和出端口，TTL 减 1 |
| 2        | `check_ttl`  | 递减后的 TTL，exact | 将选定报文送到 CPU           |
| 3        | `dmac`       | 下一跳 IPv4，exact  | 设置目的 MAC                 |
| 4        | `smac`       | 输出端口，exact     | 设置源 MAC                   |

路由表执行 `Drop_action` 时，本地版本根据 `action_run` 直接返回。后续仍按输出端口检查丢弃或 CPU 路径，避免继续查询不适用的表。`nextHop` 的初值 0 只用于确定临时变量的初始状态，实际转发仍须先由 `Set_nhop` 写入下一跳。

源码没有安装普通表项。路由表和两张 MAC 表的初始默认动作都是 `Drop_action`。要完成正常转发，需要在支持 VSS 的控制平面中配置目的前缀、下一跳、物理出端口和两侧 MAC。这些普通默认动作未声明为 `const`，本地参考版保留了规范中可由控制平面调整的形式。

`check_ttl` 的固定默认动作是 `NoAction`，并没有内置“TTL 为 0 就送 CPU”的表项。要实现规范文字描述的超时路径，还必须配置 **`0 → Send_to_cpu`**。下面是该配置存在、路由及 MAC 表齐备时的控制流分析：

| 输入 TTL | 执行 `Set_nhop` 后 | 后续处理                                    |
| -------- | ------------------ | ------------------------------------------- |
| 64       | 63                 | TTL 表未命中，继续查询 MAC 表               |
| 1        | 0                  | TTL 表命中，选择 CPU 输出，CPU 接收原始报文 |
| 0        | 255                | 8 位无符号减法回绕，不能被 TTL=0 表项识别   |

因此，这份参考程序的 TTL 处理有明确的教学边界。若将其用于实际转发，应在递减前单独处理 TTL 为 0 的输入，并明确定义 TTL 超时策略。设置 CPU 端口不会自动生成 ICMP Time Exceeded，控制平面还需完成相应处理。若未配置上述 TTL 表项，输入 TTL 为 1 的报文也可能以 TTL 0 继续走普通转发路径。

## 本地检查

从**仓库根目录**执行，无需 sudo：

```bash
p4test --version
p4test --std p4-16 examples/vss/vss.p4
```

本机 `p4test` 会执行解析、类型检查及编译器前中端处理，可以检查动作列表、参数方向和包实例装配。它不会运行报文，也不会实现 `Checksum16`。检查成功不等于得到 BMv2 可加载的配置，`p4test` 导出的编译器 IR JSON 也不是 BMv2 数据平面 JSON。

本机检查返回 0，仅报告 `REAL_PORT_COUNT`、重循环端口和 CPU 输入端口等架构常量未使用。它们用于保留完整接口，其中部分功能未被这份 IPv4 程序采用。没有通过屏蔽全部告警来替代检查。

本机 `p4c` 驱动的已安装目标中没有名为 `p4test` 的目标，应直接调用 `p4test`，不要使用 `p4c --target p4test`。将此程序交给 `p4c-bm2-ss` 会因顶层包不是 `V1Switch` 而失败，仅更换编译选项或头文件不能完成架构移植。

## 阅读与扩展

本例未检查 IPv4 `totalLen` 与实际输入长度的关系，也未实现 ARP、ICMP 错误生成、MTU 处理和传输层校验和验证。它展示的是架构接口如何与 P4 程序配合，不能替代完整 IPv4 路由器的协议处理要求。

- 对照[第 10 章](../../docs/10-架构与包.md)，区分 P4 接口声明与规范对固定功能模块的文字约定。
- 对照[示例 03](../03-ipv4-router/README.md)，分析如何在 V1Model 中传递解析错误、选择输出端口和更新校验和。
- 设计 TTL 处理的扩展时，分别讨论正常转发、TTL 0、TTL 1 和 CPU 收包内容，不要只观察 TTL 减法本身。

实测工具：p4c／p4test `1.2.5.10`。本轮验证范围为静态检查与目标接口诊断，未进行 VSS 数据平面运行测试。
