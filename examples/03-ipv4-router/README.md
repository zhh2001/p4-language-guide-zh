# 示例 03 · IPv4 静态路由转发

本例用三张表完成目的 IPv4 查找、下一跳 MAC 查询和出端口源 MAC 改写。正常转发时 TTL 减 1，再更新 IPv4 报头校验和。程序只处理无 VLAN、IHL 为 5 的 IPv4 报文，是一个静态转发实验，不是完整的 IPv4 路由器实现。

解析、表调用和流水线分别见[第 6 章](../../docs/06-Parser解析器.md)、[第 8 章](../../docs/08-匹配动作表.md)和[第 11 章](../../docs/11-V1Model架构.md)。

## 拓扑与地址

```text
h1 ── 10.0.1.0/24 ── 端口 1 [s1] 端口 2 ── 10.0.2.0/24 ── h2
```

| 项目         | h1 一侧             | h2 一侧             |
| ------------ | ------------------- | ------------------- |
| 主机 IPv4    | `10.0.1.1/24`       | `10.0.2.2/24`       |
| 主机 MAC     | `00:00:00:00:01:01` | `00:00:00:00:02:02` |
| 主机默认网关 | `10.0.1.254`        | `10.0.2.254`        |
| 网关 MAC     | `00:00:00:01:01:01` | `00:00:00:02:02:02` |
| BMv2 端口    | 1                   | 2                   |

每台主机位于独立的 network namespace 中，经 veth 连接到 BMv2。主机侧接口名为 `eth0`，命名空间和交换机侧接口名称由脚本生成。脚本不调用 Mininet。

网关 IP 用于主机的路由选择，脚本为它配置永久邻居项。本例不在交换机侧 Linux 接口上配置这些 IP，也不会回应发给网关的 ARP 或 ping。网关 MAC 由 P4 的 `smac` 表写入输出帧，不需要等于 veth 接口自身的 MAC。

## 三张表怎样配合

| 表                   | 匹配键              | 成功动作                 |
| -------------------- | ------------------- | ------------------------ |
| `MyIngress.ipv4_lpm` | 目的 IPv4，LPM 匹配 | 设置下一跳 IP 与输出端口 |
| `MyIngress.arp`      | 下一跳 IP，精确匹配 | 改写以太网目的 MAC       |
| `MyIngress.smac`     | 输出端口，精确匹配  | 改写以太网源 MAC         |

`arp` 沿用源码中的名称，实际是预配置的邻居映射表。它不会发送 ARP 请求、处理 ARP 应答或自动学习。主机的 Linux 邻居表与 P4 的这张表也不是同一个对象。

三张表的默认动作都固定为丢弃，表项也可显式选择 `drop`。Ingress 根据 `action_run` 判断能否进入下一步，避免把“命中了丢弃表项”当成查找成功。代码不依赖 511 这一默认丢弃端口值，只有三次查找均选择转发动作后才递减 TTL。

默认配置只安装 `10.0.1.1/32` 和 `10.0.2.2/32` 两条主机路由。这里的下一跳就是直连主机本身，不能把整个 `/24` 的所有目的地址都映射成这一台主机。`ipv4_lpm` 仍支持不同长度的前缀，转发远端网络时应把下一跳配置为能继续转发的相邻路由器。

## 输入检查与校验和

Parser 提取 Ethernet 和固定长度的 IPv4 报头，并检查：

- `version == 4`，`ihl == 5`。
- `totalLen >= 20`。
- `totalLen` 不超过实际输入中 Ethernet 头之后的字节数。

提取失败或上述检查失败都会记录解析错误，由 Ingress 显式丢弃。非 IPv4、VLAN、TTL 为 0 或 1、IPv4 报头校验和错误也会被丢弃。不能通过重新计算输出校验和来掩盖输入错误。

校验和计算元组没有包含原 `hdrChecksum`，因此更新前不必清零。只修改 TTL 不影响 TCP/UDP 的伪首部，传输层字节保持不变。程序不验证传输层校验和，接口语义见[附录 D](../../appendix/D-常见问题.md#d24-修改-ipv4-字段后校验和不正确)。IPv4 的长度与校验和定义见 [RFC 791 第 3.1 节](https://www.rfc-editor.org/rfc/rfc791.html#section-3.1)。

对于无选项的 IPv4 分片，程序按每片的目的地址独立转发，保留分片字段和负载，不执行重组或重新分片。输入中超出 `totalLen` 的尾部字节也会随 BMv2 未解析负载保留，不会按 IP 总长度自动裁去帧尾字节。

## 编译与运行

依赖 `p4c-bm2-ss`、`simple_switch`、`simple_switch_CLI`、`ip`、`ping`、`timeout`，以及支持 `os.setns` 的 Linux Python 3.12+。验证脚本只使用 Python 标准库。安装说明见[第 1 章](../../docs/01-环境搭建.md)。

从**仓库根目录**执行：

```bash
bash examples/03-ipv4-router/build.sh
sudo bash examples/03-ipv4-router/run.sh
```

`build.sh` 默认在示例目录生成 `router.json` 与 `router.p4info.txtpb`，也可用第一个参数指定输出目录。此次实验通过 Thrift CLI 配置，P4Info 不参与运行。

`run.sh` 每次将当前源码编译到临时目录，然后创建两台主机，配置默认路由与永久邻居项，启动 BMv2 并等待本进程的 Thrift 服务。配置文件中的注释和空行会先被过滤，避免 CLI 报错或重复执行上一条命令。脚本检查 CLI 错误输出，并读回三张表。

[runtime/s1-commands.txt](./runtime/s1-commands.txt)只适用于尚未配置过的新实例，不应直接重定向给 CLI 或重复加载。默认 Thrift 端口为 9090，已被占用时脚本在创建拓扑前退出。可以另选空闲端口：

```bash
sudo env P4_ROUTER_THRIFT_PORT=9091 bash examples/03-ipv4-router/run.sh
```

## 自动验证

[verify.py](./verify.py)通过两个主机命名空间发送原始帧，检查实际输出端口，并逐字节比较 MAC、TTL、IPv4 校验和及负载。它按负载中的随机标识及其位置识别测试帧，排除本机发包记录和引用了测试负载的 ICMP 错误报文。

两个方向各执行以下检查，共 42 个用例：

| 检查                           | 每个方向的用例数 | 预期结果                                |
| ------------------------------ | ---------------- | --------------------------------------- |
| 60、128、1514 字节帧           | 3                | 正确改写 MAC，TTL 减 1，IPv4 校验和有效 |
| TTL 为 2、255                  | 2                | 分别输出 TTL 1、254                     |
| UDP、首片、后续片、帧尾填充    | 4                | 转发成功，对应负载与其他字段保持不变    |
| TTL 为 0、1                    | 2                | 丢弃                                    |
| 错误版本、IHL 小于 5、带选项   | 3                | 丢弃                                    |
| IP 总长度过小或超过实际输入    | 2                | 丢弃                                    |
| 无路由、同网段未配置的其他主机 | 2                | 丢弃                                    |
| 错误报头校验和、非 IPv4、VLAN  | 3                | 丢弃                                    |

帧长不含 FCS。转发用例最多等待 3 秒，收到预期输出后再观察 0.3 秒，检查其他端口和重复副本。丢弃用例观察 0.3 秒。这些用例验证观察窗口内的功能行为，不测性能。

随后执行双向 ping，每个方向发送两次请求。主机已使用永久邻居项，因此 ping 成功不能作为动态 ARP 已实现的证据。配置失败、报文不符或 ping 未全部完成都会返回非零状态。全部通过后输出：

```text
PASS：IPv4 转发、报头检查、TTL、校验和及双向 ping 验证完成
```

## 手工观察与清理

```bash
sudo bash examples/03-ipv4-router/run.sh --keep
```

验证通过后保留拓扑，脚本打印抓包、ping、CLI 连接和重新验证命令。可在 CLI 中执行 `table_dump MyIngress.ipv4_lpm`、`table_dump MyIngress.arp`、`table_dump MyIngress.smac` 查看实际配置。

正常退出、报错、SIGINT 或 SIGTERM 时，脚本只停止自己启动的 BMv2，并删除本次创建的接口、命名空间和临时目录。`--keep` 模式下用 Ctrl+C 结束，手工启动的抓包程序应先停止。需要保留编译产物或日志时，请在退出前复制脚本打印的临时目录。

## 适用范围与练习

本例没有实现网关本机协议栈、ARP 处理、ICMP 错误报告、IPv4 选项、MTU 检查、分片生成和动态路由，也没有完整检查源地址、目的地址及入端口 MAC 归属。它只演示受控实验拓扑中的静态转发流程。完整路由器的要求远多于这些检查，参见 RFC 1812。

- 增加不同长度的路由前缀，验证最长前缀优先，再分别删除路由、邻居和源 MAC 表项，检查各阶段能否停止转发。
- 扩展 TTL 超时处理时，需要生成或上送足够的信息以构造 ICMP Time Exceeded 报文。设置 CPU 端口本身不会产生 ICMP 应答，控制器收发接口见[第 15 章](../../docs/15-P4Runtime控制平面.md)。
- 实现动态邻居解析时，需要补充 ARP 请求、应答、表项更新和超时处理，不能只把静态表项改成由 P4Runtime 写入。
- 增加第二台路由器时，h1→s1→s2→h2 经过三段链路、两台转发设备。应分别验证两个路由器的 TTL 递减及双向路由。

实测环境：Ubuntu 24.04 / WSL2，p4c `1.2.5.10`、BMv2 `1.15.0`、Python `3.12.3`。
